# План проверки релиз-кандидата

Этот документ разделяет три разных вида проверки: автоматические тесты кода, ручную приёмку внешней системы и LLM-evals. Пустой чекбокс означает «не проверено»; прошлые прогоны не переносятся на новый релиз-кандидат автоматически.

Дата/версия: __________  Среда: staging / production  Проверяющий: __________

## Правила безопасности

- Сначала пройти staging. Production smoke выполнять только после отдельного разрешения и в согласованное окно.
- Использовать тестовые Telegram-аккаунты и вымышленные персональные данные. Настоящие ПД в зарубежный LLM не отправлять.
- Реальную запись, перенос или отмену в YCLIENTS выполнять только в выделенном sandbox/test-филиале либо после явного разрешения владельца.
- После теста вернуть бота и интеграции в исходное состояние, сохранить время, ID тестового чата/записи и скриншоты без секретов.
- Не отмечать ручной пункт по результату автотеста и не отмечать eval по единичному ручному диалогу.

## A. Автоматические проверки кода

Эти проверки запускает разработчик локально через Docker. Они не заменяют разделы B и C.

- [ ] Полный `pytest`-набор проходит на точном commit релиз-кандидата.
- [ ] Regression-тесты подтверждают: авторизацию `/logs/tail`, идемпотентность consent callback, атомарную запись/перезагрузку промпта и явную ошибку при недоступных файловых логах.
- [ ] Regression-тесты подтверждают: явного PostgreSQL user при restore, автоматический ежедневный backup, подключение `AlertRouter` и отсутствие polling-пути в runtime.
- [ ] Compose-конфигурация валидируется с release `.env`; образы собираются; миграции и healthchecks проходят в изолированной среде.
- [ ] Static/lint/security gates проекта проходят без новых предупреждений.

## B. Ручные проверки человеком

Ни один пункт ниже в рамках текущей кодовой задачи не считается пройденным.

### B1. Staging smoke и Telegram-приёмка

- [ ] Webhook указывает на staging, секрет проверяется, контейнеры healthy; polling не запущен и второй экземпляр update не обрабатывает.
- [ ] Новый пользователь видит consent до первого LLM-вызова; повторный клик по одной кнопке и повторная доставка `Готово` не меняют выбор, не создают дубликаты и не запускают два ответа.
- [ ] `/start`, обычный вопрос, продолжение контекста, два быстрых сообщения, длинный текст и фото/стикер дают ожидаемый UX без дублей.
- [ ] Pause/resume в админке реально останавливает и возвращает ответы; после проверки бот оставлен в исходном состоянии.
- [ ] Два Telegram-аккаунта одновременно не смешивают контекст, consent, записи и ответы.
- [ ] Диалог, порядок сообщений, статистика и технический статус корректно отражаются в админке.
- [ ] `/logs/tail` без сессии получает отказ/редирект; после входа показывает хвост. При отсутствующем `bot.log` UI явно сообщает об этом и не скрывает предупреждение автообновлением.
- [ ] Сохранение валидного промпта в админке атомарно применяется к runtime; при искусственно недоступном reload UI показывает ошибку, а бот продолжает работать на последней валидной версии.

### B2. Реальные внешние интеграции

- [ ] В YCLIENTS sandbox пройден полный lifecycle: поиск слота → создание → чтение → перенос → отмена; проверены timezone, филиал, услуга и отсутствие дублей при повторе webhook/task.
- [ ] Реальные Telegram Bot API webhook/setWebhook, ответы, callback query и rate-limit поведение проверены на staging-токене.
- [ ] Реальный LLM-провайдер принимает только замаскированные тестовые данные; в provider request/logs нет исходных телефонов, email и ФИО.
- [ ] Redis, PostgreSQL и RabbitMQ переживают контролируемый restart без потери/двойной обработки подтверждённых задач.
- [ ] Если включены scheduler/уведомления, тестовое уведомление приходит один раз и в правильное локальное время.

### B3. Backup/restore drill

- [ ] Автоматический backup-сервис сам создаёт зашифрованный backup по расписанию без ручного запуска.
- [ ] В отдельную пустую тестовую PostgreSQL восстановлен выбранный backup с явно заданным `POSTGRES_USER`.
- [ ] После restore сверены миграционная версия, контрольные количества и несколько тестовых сущностей; секрет шифрования не попал в логи/артефакты.
- [ ] Зафиксированы RPO/RTO, дата backup, длительность restore и ответственный; production-база не затронута.

### B4. Получение алерта человеком

- [ ] Контролируемая техническая ошибка worker приводит к одному Telegram-алерту в технический чат; человек подтверждает получение, понятный код/контекст и отсутствие ПД/секретов.
- [ ] Повтор ошибки в dedup-окне не спамит; после окна новый алерт приходит.
- [ ] Ошибка самого канала алертов не скрывает исходную ошибку задачи и видна в runtime-логах.
- [ ] Если есть бизнес-алерты, тестовое бизнес-событие приходит только в разрешённый чат и не смешивается с техническим.

### B5. Production smoke — только после отдельного разрешения

- [ ] Развёрнут точный проверенный commit; миграции завершены; все production healthchecks зелёные.
- [ ] Один безопасный Telegram-диалог проходит consent → ответ → сохранение истории без реальной записи и настоящих ПД.
- [ ] Админка, pause/resume, защищённые логи, метрики и получение тестового алерта доступны назначенным людям.
- [ ] Последний автоматический backup свежий; rollback-команда и ответственный подтверждены до smoke.
- [ ] После smoke нет новых `ERROR/CRITICAL`, дублей updates/tasks и незапланированных внешних мутаций.

## C. LLM-evals

Evals запускаются отдельным воспроизводимым набором на зафиксированных dataset, моделях и настройках. Текущая кодовая задача их не запускала.

- [ ] Основная модель: фактическая точность по услугам/ценам, тон, удержание контекста, медицинские границы и честный отказ при нехватке данных.
- [ ] Роутер: правильный выбор основной/резервной модели и инструментов по классу запроса; отдельно измерены false route и недоступность маршрута.
- [ ] Output validator: блокирует невалидный формат, неподтверждённую запись, опасные утверждения и утечку служебных данных; валидные ответы не режет.
- [ ] Guardrails/PII: jailbreak, prompt extraction, obfuscated attacks, телефон/email/ФИО и смешанные кейсы; проверены и recall блокировок, и false positives.
- [ ] Fallback/reserve: timeout, 429, 5xx и невалидный ответ основной модели приводят к ограниченному fallback без дубля внешнего действия; полный отказ даёт безопасную заглушку.
- [ ] Зафиксированы dataset version, модели/провайдеры, judge, пороги, число кейсов, pass rate, критичные провалы и ссылка на артефакт прогона.

## Дефект и критерий выпуска

Для дефекта записать: среду и commit, время МСК, тестовый аккаунт/ID без ПД, точные шаги, ожидаемое/фактическое, screenshot/log correlation ID и критичность.

Релиз готов только когда автоматические gates зелёные, обязательные staging/manual пункты и все пять групп evals пройдены на одном release candidate, backup/restore drill доказан, человек получил тестовый алерт, а production smoke либо явно разрешён и пройден, либо остаётся формально назначенным внешним gate.

# Reactivation V2 UI Implementation Plan

> **Для выполнения:** использовать `executing-plans` и проходить этапы последовательно. Subagents не нужны: изменение компактное и затрагивает один шаблон, один CSS-файл и focused-тесты.

**Цель:** превратить owner-only страницу Reactivation V2 в понятный рабочий сценарий «настроить → рассчитать → проверить → подтвердить → запустить», не меняя бизнес-логику и backend-контракты.

**Подход:** переработать только Jinja-разметку, scoped CSS и минимальный JavaScript для условного поля напоминания и признака несохранённых изменений. Все существующие POST-маршруты, CSRF/RBAC, формы, названия полей, eligibility, consent, scheduler, outbox и метрики остаются прежними.

**Стек:** Jinja2, существующий CSS админки, нативный JavaScript без зависимостей, FastAPI/httpx tests, Docker Compose.

## Глобальные ограничения

- Работать только в ветке/worktree `codex/reactivation-v2-ui`, созданной от актуального `origin/main@5e3438f` или более свежего состояния после обязательного `git fetch`.
- Не менять `reactivation_database.py`, domain/service-код, БД, миграции, API, eligibility, consent, STOP, scheduler, worker и доставку.
- Не добавлять зависимости, frontend-framework, сборщик, новые маршруты или универсальные UI-компоненты «на будущее».
- Не выполнять реальные Telegram, YCLIENTS или LLM-вызовы; не активировать программу и не менять staging/production.
- Терминология остаётся честной: Telegram только «принял» сообщение; UI не заявляет доставку или прочтение.
- Все проверки и локальный preview запускать только через Docker.

## Критерий готовности

Владелец с первого экрана понимает состояние программы и следующий шаг; технические термины не требуют расшифровки; опасная кнопка не предлагается в остановленном режиме; настройки, preview и запуск образуют один сценарий; воронка показывает честный бизнес-результат; technical/legal details доступны, но не перегружают страницу; desktop/mobile и существующие backend/security-контракты проходят проверки.

# Событийный журнал клиента — дизайн

## Цель

Добавить в существующую карточку диалога единую хронологическую ленту действий клиента, бота и фоновых процессов. Лента должна стать read-only основой для будущего профиля клиента и отдельного экрана записи.

## Границы первой версии

- Журнал доступен авторизованным `owner` и `admin` на странице `/chats/{chat_id}`.
- На странице показывается не более 50 событий; старые страницы открываются через `events_offset`.
- Новая универсальная таблица событий не создаётся.
- Рабочие процессы бота, Telegram, YCLIENTS, scheduler и worker не меняются.
- Журнал не является административным audit-log и не заменяет `admin_audit_events`.
- Фильтры, поиск, экспорт и редактирование событий не входят в первую версию.

## Источники

Лента строится одним read-only запросом из уже существующих таблиц:

1. `messages` по `chat_id`: сообщения клиента и бота.
2. `booking_events` через `booking_scenarios.customer_id`: этапы создания, переноса и отмены записи.
3. `scheduler_jobs`: строковый `payload.customer_id` является каноническим владельцем; только при его отсутствии используется связь `booking_key` → `bookings.customer_id`. Показываются создание задачи и её терминальный результат.
4. `escalations` по `customer_id`: открытие и закрытие обращения к человеку.
5. `human_mode` по `customer_id`: включение текущего ручного режима.
6. `admin_audit_events` только когда `object_type = 'customer'` и `object_id = chat_id`: будущие адресные действия администратора.

Обезличенная запись `customer_data.delete` намеренно не связывается обратно с удалённым клиентом и в его ленту не попадает.

## Модель представления

Каждый источник нормализуется в один словарь:

```python
{
    "event_id": "message:123",
    "occurred_at": datetime,
    "category": "message",
    "kind": "message.user",
    "title": "Сообщение клиента",
    "description": "Текст сообщения",
    "status": None,
}
```

Допустимые категории первой версии: `message`, `booking`, `notification`, `handoff`, `admin`. `event_id` составляется из имени источника и первичного ключа, чтобы одинаковое время не нарушало стабильную сортировку.

## Безопасное отображение

- Текст сообщения берётся только из `messages.content`, который уже доступен на этой странице.
- Для booking, scheduler, escalation и admin событий UI получает только явно выбранные поля: тип, статус, время и безопасный код причины.
- JSON payload, idempotency keys, IP, user-agent, токены, телефоны, служебные ошибки и полные snapshots не передаются в шаблон.
- Неизвестный внутренний `kind` отображается как нейтральное «Системное событие», без raw payload.
- Все значения выводятся обычным Jinja escaping; HTML из БД не помечается `safe`.

## Получение данных

В `admin/database.py` добавляется `get_customer_events(chat_id, limit=50, cursor=None)`. Функция валидирует `limit` (`1..50`) и bounded opaque URL-safe cursor, выполняет SQL `UNION ALL`, сортирует по `occurred_at DESC, source DESC, source_id DESC` и запрашивает `limit + 1` строку. Кнопка «Раньше» использует одностороннюю keyset-границу по полному sort key, поэтому новое или поздно зафиксированное событие не дублируется на следующей странице. Возврат к свежим событиям выполняется возвратом/перезагрузкой карточки. Cursor не содержит клиентских данных.

Карточка диалога продолжает получать сообщения и статистику существующим `get_chat_detail`. Route отдельно запрашивает страницу событий и передаёт её в шаблон. Это не смешивает профиль диалога с timeline-query и не меняет существующий контракт сообщений.

## Интерфейс

После статистики и перед текущим разделом «Сообщения» появляется блок «События клиента»:

- дата и время;
- цветная метка категории;
- человекочитаемый заголовок;
- короткое описание или статус;
- ссылки «Новее» и «Раньше», когда соответствующая страница существует.

На пустой ленте показывается «Событий пока нет». Действующая danger zone удаления остаётся внизу страницы и не меняется.

## Ошибки и совместимость

- Некорректный `events_offset` возвращает HTTP 422 через штатную валидацию FastAPI.
- Ошибка БД обрабатывается существующей границей админки; частично сформированный журнал не показывается.
- События удалённого клиента исчезают вместе с исходными строками согласно уже реализованному deletion manifest.
- Миграция БД и новая зависимость не требуются.

## Проверки

1. Integration: события разных источников объединяются, сортируются и ограничиваются одним клиентом.
2. Integration: пагинация стабильна, `limit` не превышает 50, raw payload не попадает в результат.
3. E2E admin: owner и admin видят ленту; неизвестный chat остаётся 404; invalid offset даёт 422.
4. Template/unit: категории, пустое состояние, ссылки страниц и escaping отображаются корректно.
5. Regression: существующие сообщения, статистика и owner-only удаление данных работают без изменений.

## Критерии готовности

- В карточке диалога видна единая лента последних 50 событий.
- Источники не изменяют свои write-paths.
- В шаблон не передаются технические payload и секретные служебные поля.
- Полный Docker pytest проходит.
- Независимое ревью не содержит Critical или Important замечаний.

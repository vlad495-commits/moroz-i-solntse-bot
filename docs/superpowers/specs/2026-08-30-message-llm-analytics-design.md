# Пометочная LLM-аналитика сообщений — дизайн

## Цель

В деталях диалога администратор должен видеть точный LLM-расход обработки каждого нового входящего сообщения пользователя: совокупные метрики всей цепочки и расшифровку по фактически выполненным модулям. Сообщения без LLM-вызова должны отличаться от старых сообщений, для которых точной связи исторически не существовало.

## Границы

- Аналитика относится к одной сохранённой записи `messages` с ролью `user`. Если Telegram buffer объединил несколько updates в один текст, это одна единица аналитики.
- В состав цепочки входят все фактически сохранённые `token_usage`, включая `security`, `router`, `compact`, `answer`, `validator` и совместимый `legacy` purpose.
- Под сообщением показываются общие вызовы, prompt/completion/total/cached tokens, стоимость и экономия, а также разбивка по purpose и модели.
- Не вызванный модуль не добавляет токены и не рисуется как состоявшийся вызов. Если вся цепочка пуста, показывается `LLM не вызывалась`.
- Ответы ассистента не дублируют аналитику.
- Общая статистика диалога, списка диалогов и глобальная статистика сохраняют нынешнее поведение и продолжают учитывать старые `token_usage`.
- Старые данные не сопоставляются по времени и не backfill-ятся приблизительно.
- Внешние provider-вызовы, новые зависимости и отдельная аналитическая таблица не нужны.

## Модель данных

Additive migration `0020_message_llm_analytics` добавляет:

- `messages.llm_usage_tracked BOOLEAN NULL` без server default;
- `token_usage.source_message_id BIGINT NULL` с внешним ключом на `messages.id` и `ON DELETE CASCADE`;
- индекс по `token_usage.source_message_id` для страницы деталей диалога.

Семантика трёх состояний пользовательского сообщения:

1. `llm_usage_tracked IS NULL` — точной исторической привязки нет; UI показывает `Нет точной привязки`.
2. `llm_usage_tracked IS TRUE` и связанных usage-строк нет — новый обработанный путь не обращался к LLM; UI показывает `LLM не вызывалась`.
3. `llm_usage_tracked IS TRUE` и usage-строки есть — UI показывает сумму и расшифровку.

Значение `FALSE` не используется: nullable boolean нужен только для различения старой неизвестной истории и нового наблюдаемого пути. Предыдущий worker остаётся совместим с новой схемой: его записи получают `NULL` и честно отображаются как непривязанные.

## Запись данных

В основном worker-пути пользовательское сообщение сохраняется с `llm_usage_tracked = TRUE` и возвращает свой `id`. Ответ ассистента сохраняется отдельно в той же транзакции. `_persist_token_usage` получает `source_message_id` и записывает его во все элементы `result.usage`, поэтому Security, Router, Compact, answer, Validator и возможные повторные/fallback-вызовы относятся к одному входящему сообщению.

В human mode входящее сообщение также сохраняется с `llm_usage_tracked = TRUE`, но usage-строки не создаются. Это формирует точный статус `LLM не вызывалась`.

Старые и совместимые legacy-пути, которые не передают точную связь, продолжают писать nullable-поля как `NULL`; они не выдают ложную детализацию. Ошибка записи usage внутри основной транзакции не оставляет частично помеченное сообщение.

## Чтение и расчёты

`get_chat_detail` получает сообщения и связанные usage-строки ограниченным числом запросов без запроса на каждое сообщение. Для каждого tracked user message данные группируются по паре `(purpose, model)`:

- `llm_calls` — число строк usage;
- `prompt_tokens`, `completion_tokens`, `cached_tokens`, `total_tokens` — суммы;
- `cost_usd`, `savings_usd` — сумма расчётов каждой исходной usage-строки через существующий `calculate_cost`, чтобы разные модели не смешивались под одной ценой.

Итог сообщения является суммой всех его групп. Существующий верхний chat aggregate не пересчитывается и не ограничивается только связанными строками.

## Интерфейс

Под каждым пользовательским сообщением появляется компактный блок:

- итоговая строка: число LLM-вызовов, total tokens, стоимость и экономия;
- строка токенов: prompt, completion и cached;
- список фактических групп purpose/model с числом вызовов и их токенами;
- один из нейтральных статусов вместо цифр: `LLM не вызывалась` или `Нет точной привязки`.

Названия purpose отображаются человекочитаемо (`Security`, `Router`, `Compact`, `Answer`, `Validator`, `Legacy`), неизвестное значение безопасно показывается как сохранённая строка. Блок не раскрывает prompt, masked context, provider response или другие чувствительные данные. Существующие роли доступа и аудит просмотра чата не меняются.

## Совместимость и удаление

- Миграция добавляющая; существующие строки остаются валидными.
- Downgrade удаляет индекс, внешний ключ и два новых столбца, не изменяя старые данные.
- Текущее удаление данных клиента сохраняется; каскадная связь дополнительно предотвращает orphan usage при удалении сообщения.
- Retention и chat totals продолжают работать по `chat_id`.
- Rollout выполняется schema-first, затем новые worker/admin images; предыдущие images не зависят от новых полей.

## Проверка

Реализация идёт test-first через Docker:

1. Migration tests подтверждают additive upgrade/downgrade, nullable legacy-состояние, FK и индекс.
2. Worker unit/integration tests сначала падают, затем подтверждают один `source_message_id` для всей usage-цепочки и tracked-сообщение без usage в human mode.
3. Admin database tests подтверждают три состояния, общую сумму, группировку по purpose/model и отсутствие N+1.
4. Pricing tests подтверждают суммирование стоимости по исходным моделям каждой usage-строки.
5. Route/template tests подтверждают блок только под user messages, понятные статусы и неизменную верхнюю статистику диалога.
6. Focused Docker regression охватывает migration, worker, admin, deletion и retention; затем выполняются общий релевантный regression и Compose config check.

## Критерии готовности

- Для каждого нового сохранённого пользовательского сообщения статус LLM однозначен.
- Все usage одной обработки связаны с правильным сообщением и отражены одновременно итогом и разбивкой.
- Старые сообщения не получают приблизительных или ложных нулевых значений.
- Старые chat/global aggregates продолжают показываться.
- Сообщения и usage удаляются без нарушения privacy/retention контрактов.
- Все согласованные Docker-проверки проходят; staging и production не изменяются без отдельного шага.

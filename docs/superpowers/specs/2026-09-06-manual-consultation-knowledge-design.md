# Первый пакет: консультации по ручной базе знаний

Дата: 2026-09-06. Границы узкого пакета согласованы владельцем. Последующее решение владельца: кандидат по имеющимся сведениям принят как временная содержательная база; ответы Светы внесём позже. Неизвестные/спорные условия остаются неизвестными и не блокируют архитектурную реализацию. Исходный [доказательный аудит](<../../audits/Аудит упрощения архитектуры по Lucky Hair 2026-09-06.md>) — фронт работ, эта spec — первый пакет, [план](../plans/2026-09-06-reference-simplification.md) — порядок исполнения. Rollout и платные/live проверки требуют отдельного разрешения. Текущий статус — только в `Дорожная карта.md`.

## Решение из истории обсуждения

Выбран поэтапный перенос принципов референса: ручной промпт → основной LLM для консультаций, детерминированные действия для записи, существующий редактор знаний. Полный откат к старому меню отвергнут: он возвращает удалённые пути и теряет свободное заполнение записи. Router не переписывается одновременно с первым пакетом, чтобы отдельно проверить сценарии свободного заполнения и смешанных запросов. Наличие потребителей сущностей и тем не оправдывает их сохранение само по себе: следующий этап обязан сравнить нужный клиентский результат с более простым паттерном референса, включая упрощение потребителя. Новая CMS, RAG и orchestration framework не нужны. Исходный фронт работ заново согласовывать не требуется.

Кандидат: `tmp/manual-consultation-system-draft-2026-09-06.md`, v1.8-draft.2. При реализации перенести его в `project/llm/prompts/system.md` согласованно с удалением consultation grounding, а не применить файл отдельно к старому pipeline. Отсутствие ответов Светы не означает разрешение заполнять неизвестные цены. Отправку вопросов подтвердил владелец; автоматически связываться с заказчицей не нужно.

## Цель и границы

Основной LLM свободно отвечает об услугах, стоимости, длительности, подготовке и ограничениях только по активному вручную редактируемому системному промпту. YCLIENTS используется для технического сопоставления услуги, специалистов, доступности, слотов и операций записи. Не создаём второй автоматический прайс, RAG, CMS, таблицу знаний или новую прослойку orchestration.

Первый пакет не меняет Router V3, durable inbox/outbox, consent/privacy/security, BookingService, scheduler уведомлений, существующие подтверждения и интерфейс начала записи. Контекстные кнопки и последовательные уточнения допустимы. Полный rollback и восстановление большого меню исключены из пакета.

### 1.1. Поминутные услуги: одна услуга, один тариф

Уточнение владельца 2026-09-06: технические карточки «1 минута», «3 минуты», … не превращать в публичный список самостоятельных услуг. Организовать консультационную KB по смысловым услугам: описание, единица оплаты, тариф, существенные условия. Для фиксированных процедур — цена за сеанс/вариант; для поминутных — цена минуты; для пакетов/депозита — отдельно подтверждённые условия, не механическое копирование полей записи.

Текст правила для включения в будущий основной промпт:

> Поминутные варианты одной процедуры представляй как одну услугу с тарифом за минуту. Разовый тариф: солярий — 42 ₽/мин, коллариум — 51 ₽/мин, коллагенарий — 42 ₽/мин. На общий вопрос о цене назови тариф только запрошенной услуги; не перечисляй стоимость каждой возможной длительности. Если клиент указал число минут, дай стоимость только этого варианта по подтверждённому тарифу, коротко: «10 минут солярия — 420 ₽». Если клиент явно сравнивает несколько длительностей, сравни только названные варианты. Подробную таблицу давай лишь по прямому запросу на неё. Не смешивай разовый тариф с неподтверждёнными льготами/депозитом. Расчёт стоимости не означает рекомендацию длительности, доступность услуги или подтверждение записи.

Примеры целевого ответа:

- «Сколько стоит солярий?» → «Солярий — 42 ₽ за минуту». Не добавлять перечень длительностей и не задавать обязательный вопрос, если запрос уже закрыт.
- «А 10 минут?» при однозначном контексте солярия → «10 минут — 420 ₽».
- «Что по ценам на солярий и коллариум?» → «Солярий — 42 ₽/мин, коллариум — 51 ₽/мин».
- «Сравни 5 и 10 минут солярия» → «5 минут — 210 ₽, 10 минут — 420 ₽». Без остальных вариантов.

Цены в примерах взяты из серверного snapshot 2026-09-06 06:00 МСК. При обновлении ручного тарифа примеры не должны оставаться конкурирующим старым прайсом: обновлять согласованно или исключить конкретные суммы из примеров.

Технические ID/варианты YCLIENTS остаются у booking coordinator. Отсутствие карточки определённой длительности не доказывает запрет арифметического расчёта, но запрещает обещать возможность записи на неё без проверки. Не предлагать более долгий сеанс ради продажи.

Отдельный gate реализации: существующий numeric allowlist не умеет выводить все произведения из цены минуты. Обеспечить прохождение корректных расчётов по подтверждённому тарифу и отказ для неверных без отключения price validation и без раздувания пользовательского ответа. Минимальное решение выбрать при реализации по существующим validator-потребителям; если потребуется поддержка производных сумм, ограничить её тарифом/длительностью и проверить обновление тарифа. Не возвращать ради этого YCLIENTS grounding или второй автоматически поддерживаемый прайс.

Конкретизация для реализации: производные суммы не включаются глобально в allowlist. Проверяется каждое вхождение расчёта с привязкой к услуге и длительности; та же сумма рядом с другой услугой не получает разрешение автоматически. Тарифы извлекаются только из явных строк активного ручного промпта. Допустимо уточнить короткий пример до «10 минут солярия — 420 ₽», если это необходимо для надёжной проверки; длинная таблица при этом не появляется. Фиксированные цены по-прежнему требуют содержательной проверки, один numeric validator не доказывает их правильную привязку.

Граница: небольшой проверяемый формат тарифной строки и расчёта, а не универсальный парсер естественного языка. Не добавлять DSL/JSON, словари скидок, пакетов и бесконечные исключения. Неподдержанный ответ проходит ограниченный retry в понятном формате либо безопасное уточнение. Обычная замена цены собственницей через editor должна применяться без разработчика, правки regex или второго прайса; это отдельный acceptance-сценарий save → reload → новый расчёт, старый расчёт не принимается как актуальный. Числовые примеры не должны заставлять вручную искать все дубли тарифа: обновлять согласованно либо убрать дублирование изменяемых сумм.

Добавочные acceptance-сценарии: общий вопрос не выдаёт таблицу; конкретные минуты дают только нужную сумму; сравнение не разрастается; неверное произведение отклоняется; новый тариф после reload даёт новый расчёт; расчёт не подтверждает слот и не рекомендует длительность процедуры.

### 2. Удаление consultation grounding

- `project/worker/main.py`: убрать `resolve_catalog` и передачу `catalog` в answer LLM. Не удалять catalog repository из `_build_yclients_services` и Telegram coordinator.
- `project/llm/llm.py` и `project/src/moroz/security/pipeline.py`: убрать консультационный параметр/ветки `direct_reply`, `catalog_block`, merge каталожных facts. Consultation идёт в основной LLM, затем существующую validation.
- `project/admin/eval_runner.py`: тот же prompt-only контракт, без скрытого eval-only источника цен.
- `project/src/moroz/booking/catalog.py`: удалять grounding-only API лишь после проверки всех production/test consumers; сохранить `CatalogRepository.list_services`, DTO, reader, sync и техническое сопоставление. Удаление схемы/price columns не входит в пакет.
- `YCLIENTS_CATALOG_GROUNDING_ENABLED`: после удаления всех потребителей согласованно убрать устаревшую настройку/документацию либо явно оставить временно неиспользуемой для совместимости deployment. Не использовать её как выключатель YCLIENTS booking и не менять серверный env в рамках кода без отдельного rollout.

### 3. Редактирование и validator

- Переиспользовать `project/admin/prompt_routes.py`, `prompt_database.py` и `_load_prompt`/reload listener в `llm.py`. Сохранение и rollback остаются owner-only, CSRF protected и аудируемыми.
- Успешный reload означает согласованную пару prompt+facts одной версии. Уже начатый ответ может завершиться на старой версии; следующий после подтверждённого reload обязан использовать новую.
- Новая цена проходит extractor, удалённая не разрешается старыми facts. Нельзя трактовать numeric allowlist как полную семантическую проверку прайса.
- Timeout ack показывается как неподтверждённое применение. После разрыва Redis связь должна восстанавливаться без ложного success: проверить повторное применение/перезапуск; минимальную доработку resync делать только при подтверждении потери применения, без новой очереди/сервиса.
- Сохранить общий файл admin/worker, атомарную замену, проверку hash и историю версий. PostgreSQL хранит историю, не конкурирующую KB.
- Перед будущим deployment сохранить активный owner prompt и его hash/version; доставка кода не должна молча заменить его устаревшим Git-вариантом. Code rollback и content rollback — разные операции. Текущий аудит не меняет mounts и серверные файлы.

### 4. Запись и смешанные реплики

- `booking + topics` остаётся одним маршрутом. Локальный coordinator отвечает за недостающие данные/кнопки/результат действия; LLM — за консультационную часть. Минимальное соединение двух частей сохраняется.
- При недоступности answer LLM сохранять безопасный локальный booking next step с соответствующей клавиатурой; не выдавать текст, оторванный от кнопок, и не объявлять мутацию успешной без результата BookingService.
- Вопрос во время draft не стирает draft. При неясном намерении — уточнение, не автоматическое действие.
- Технический каталог сопоставляет публичное название с provider ID. При отсутствии/неоднозначности совпадения — уточнение, без выдуманного ID и выбора случайного специалиста. Отдельную alias-таблицу не строить, пока не выявлен конкретный неподдержанный случай.
- При недоступном каталоге/провайдере консультация работает; запись не подтверждается. При явном конфликте ручных условий и операционных данных не заменять консультационный прайс автоматически; сообщать необходимость проверки условий человеком.

### 5. Свежесть каталога

Сохранить существующий часовой технический sync и 24h TTL в первом пакете. Это обеспечивает поиск услуг/специалистов, а не обновление консультационных цен. Частота пересматривается отдельным небольшим решением после оценки допустимой задержки и отказов. Live-проверка слота перед мутацией не заменяется snapshot.

## Будущая проверка и acceptance

При оформлении этого документа тесты не запускались. При реализации обязательны Docker и **изолированные** тестовые БД/Redis; не повторять FLUSHDB на общей базе. Локальные fake-provider проверки входят в реализацию, paid evals и staging требуют отдельного разрешения.

| Сценарий | Ожидаемый результат |
|---|---|
| Описание / цена / длительность известной услуги | Основной LLM отвечает по активному prompt; consultation не вызывает catalog repository |
| Неизвестная цена / неподтверждённая акция | Нет выдуманного числа, есть честное уточнение |
| Owner меняет сумму, подтверждается reload | Новая сумма используется и проходит validator; старая история не переопределяет её |
| Цена другой услуги с разрешённым числом | Проверка содержания обнаруживает ошибочную привязку; numeric allowlist не выдаётся за доказательство корректности |
| Неудачный reload / разрыв Redis / rollback | UI различает сохранение и применение; прежний pipeline целостен; восстановление проверяемо |
| «Цена и запиши завтра» | Ответ на вопрос + правильный next step, один маршрут, без мутации до подтверждения |
| Answer LLM недоступен после dispatch | Сохранены локальный next step и согласованные кнопки |
| Консультационный вопрос внутри draft | Ответ дан, draft/операция не потеряны |
| Публичное название не совпадает с provider | Уточнение вместо случайного ID |
| Нет YCLIENTS / snapshot старше 24h | FAQ работает, невозможная запись не подтверждается |
| Выбор услуги/специалиста/слота; изменение предпочтений | Реальные варианты, не слепое доверие Router; stale выбор сбрасывается/отклоняется |
| Create/reschedule/cancel и replay callback | Ownership, consent, явное подтверждение, актуальность и идемпотентность сохранены |
| STOP, prompt injection, чужая запись, ПД | Существующие safety/privacy fences не ослаблены |

Тестовые области будущей правки: pipeline/validator, worker dispatch, prompt save/reload, admin eval runner и focused booking regression. Предыдущие 2344 passed не заменяют gate нового кода; известные дефекты из побочного аудита проверяются отдельно перед rollout.

## Что требуется от владельца

1. Границы пакета и последовательность «актуальный контент → отдельная реализация → отдельная проверка» согласованы 2026-09-06.
2. Текущий кандидат разрешён как временная база; ответы Светы позже уточнят содержание. Исторические и спорные суммы этим решением не утверждены и в ответы не добавляются.
3. Если менять вход в запись — отдельно выбрать свободный текст или дополнительно одну контекстную кнопку. Рекомендация первого пакета: сохранить текущий вход, не смешивать смену источника знаний с UX-переделкой.

Следующая очередь после пакета: проверить необходимость полей Router и механизмов соединения ответов по клиентским сценариям и сравнению с более простым референсом. Потребитель показывает связь, но не доказывает необходимость: можно упростить и его. Для сохранения нужны конкретный сценарий/гарантия, рассмотренная альтернатива и проверяемая потеря при её применении. Затем отдельно UX записи/частота технического sync. Не объединять всё в большой рефакторинг.

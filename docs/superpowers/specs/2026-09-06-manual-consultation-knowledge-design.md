# Первый пакет: консультации по ручной базе знаний

Дата: 2026-09-06. Статус: проект узкой спецификации для разбора владельцем; **реализация и rollout не разрешены этим документом**. Основание: решения владельца из исходного задания и [доказательный аудит](<../../audits/Аудит упрощения архитектуры по Lucky Hair 2026-09-06.md>).

## Цель и границы

Основной LLM свободно отвечает об услугах, стоимости, длительности, подготовке и ограничениях только по активному вручную редактируемому системному промпту. YCLIENTS используется для технического сопоставления услуги, специалистов, доступности, слотов и операций записи. Не создаём второй автоматический прайс, RAG, CMS, таблицу знаний или новую прослойку orchestration.

Первый пакет не меняет Router V3, durable inbox/outbox, consent/privacy/security, BookingService, scheduler уведомлений, существующие подтверждения и интерфейс начала записи. Контекстные кнопки и последовательные уточнения допустимы. Полный rollback и восстановление большого меню исключены из пакета.

## Контракты реализации

### 1. Один источник консультационных фактов

- `project/llm/prompts/system.md` содержит утверждённые собственником публичные названия/варианты, описания, цены с единицами, длительности (различая процедуру и визит), подготовку, ограничения и основания передачи человеку. Указать дату актуализации контента, не обещать полноту неутверждённых данных.
- Согласованно заменить §7, §10, зависимые пункты §11.1/§12/примеров; убрать устаревшую ссылку на меню «Мои записи» в §9.3. Не ограничиваться выключением флага grounding.
- Не копировать автоматически июльский `services_prices.md`. Собственник сверяет его как черновой источник; неизвестная цена остаётся неизвестной. История диалога, слова клиента и YCLIENTS не переопределяют ручную KB.
- Для существующего extractor каждую сумму, включая обе границы диапазона, писать с `₽` или `руб.`. Проверять не только прохождение allowlist, но и соответствие суммы услуге/варианту.
- Если факт отсутствует или противоречив внутри KB — честное уточнение/администратор, без выдуманной суммы. Медицинские ограничения и запрет обещаний лечения сохраняются.

### 2. Удаление consultation grounding

- `project/worker/main.py`: убрать `resolve_catalog` и передачу `catalog` в answer LLM. Не удалять catalog repository из `_build_yclients_services` и Telegram coordinator.
- `project/llm/llm.py` и `project/src/moroz/security/pipeline.py`: убрать консультационный параметр/ветки `direct_reply`, `catalog_block`, merge каталожных facts. Consultation идёт в основной LLM, затем существующую validation.
- `project/admin/eval_runner.py`: тот же prompt-only контракт, без скрытого eval-only источника цен.
- `project/src/moroz/booking/catalog.py`: удалять grounding-only API лишь после проверки всех production/test consumers; сохранить `CatalogRepository.list_services`, DTO, reader, sync и техническое сопоставление. Удаление схемы/price columns не входит в пакет.
- `YCLIENTS_CATALOG_GROUNDING_ENABLED`: после удаления всех потребителей согласованно убрать устаревшую настройку/документацию либо явно оставить временно неиспользуемой для совместимости deployment. Не использовать её как выключатель YCLIENTS booking и не менять серверный env в рамках кода без отдельного rollout.

### 3. Редактирование и validator

- Переиспользовать `project/admin/prompt_routes.py`, `prompt_database.py` и `_load_prompt`/reload listener в `llm.py`. Сохранение и rollback остаются owner-only, CSRF protected и аудируемыми.
- Успешный reload означает согласованную пару prompt+facts одной версии. Уже начатый ответ может завершиться на старой версии; следующий после подтверждённого reload обязан использовать новую.
- Новая цена проходит extractor, удалённая не разрешается старыми facts. Нельзя трактовать numeric allowlist как полную семантическую проверку прайса.
- Timeout ack показывается как неподтверждённое применение. После разрыва Redis связь должна восстанавливаться без ложного success: проверить повторное применение/перезапуск; минимальную доработку resync делать только при подтверждении потери применения, без новой очереди/сервиса.
- Сохранить общий файл admin/worker, атомарную замену, проверку hash и историю версий. PostgreSQL хранит историю, не конкурирующую KB.
- Перед будущим deployment сохранить активный owner prompt и его hash/version; доставка кода не должна молча заменить его устаревшим Git-вариантом. Code rollback и content rollback — разные операции. Текущий аудит не меняет mounts и серверные файлы.

### 4. Запись и смешанные реплики

- `booking + topics` остаётся одним маршрутом. Локальный coordinator отвечает за недостающие данные/кнопки/результат действия; LLM — за консультационную часть. Минимальное соединение двух частей сохраняется.
- При недоступности answer LLM сохранять безопасный локальный booking next step с соответствующей клавиатурой; не выдавать текст, оторванный от кнопок, и не объявлять мутацию успешной без результата BookingService.
- Вопрос во время draft не стирает draft. При неясном намерении — уточнение, не автоматическое действие.
- Технический каталог сопоставляет публичное название с provider ID. При отсутствии/неоднозначности совпадения — уточнение, без выдуманного ID и выбора случайного специалиста. Отдельную alias-таблицу не строить, пока не выявлен конкретный неподдержанный случай.
- При недоступном каталоге/провайдере консультация работает; запись не подтверждается. При явном конфликте ручных условий и операционных данных не заменять консультационный прайс автоматически; сообщать необходимость проверки условий человеком.

### 5. Свежесть каталога

Сохранить существующий часовой технический sync и 24h TTL в первом пакете. Это обеспечивает поиск услуг/специалистов, а не обновление консультационных цен. Частота пересматривается отдельным небольшим решением после оценки допустимой задержки и отказов. Live-проверка слота перед мутацией не заменяется snapshot.

## Будущая проверка и acceptance

Сейчас тесты не запускаются. При отдельном разрешении на реализацию использовать Docker и **изолированные** тестовые БД/Redis; не повторять FLUSHDB на общей базе. Paid evals и staging требуют отдельного разрешения.

| Сценарий | Ожидаемый результат |
|---|---|
| Описание / цена / длительность известной услуги | Основной LLM отвечает по активному prompt; consultation не вызывает catalog repository |
| Неизвестная цена / неподтверждённая акция | Нет выдуманного числа, есть честное уточнение |
| Owner меняет сумму, подтверждается reload | Новая сумма используется и проходит validator; старая история не переопределяет её |
| Цена другой услуги с разрешённым числом | Проверка содержания обнаруживает ошибочную привязку; numeric allowlist не выдаётся за доказательство корректности |
| Неудачный reload / разрыв Redis / rollback | UI различает сохранение и применение; прежний pipeline целостен; восстановление проверяемо |
| «Цена и запиши завтра» | Ответ на вопрос + правильный next step, один маршрут, без мутации до подтверждения |
| Answer LLM недоступен после dispatch | Сохранены локальный next step и согласованные кнопки |
| Консультационный вопрос внутри draft | Ответ дан, draft/операция не потеряны |
| Публичное название не совпадает с provider | Уточнение вместо случайного ID |
| Нет YCLIENTS / snapshot старше 24h | FAQ работает, невозможная запись не подтверждается |
| Выбор услуги/специалиста/слота; изменение предпочтений | Реальные варианты, не слепое доверие Router; stale выбор сбрасывается/отклоняется |
| Create/reschedule/cancel и replay callback | Ownership, consent, явное подтверждение, актуальность и идемпотентность сохранены |
| STOP, prompt injection, чужая запись, ПД | Существующие safety/privacy fences не ослаблены |

Тестовые области будущей правки: pipeline/validator, worker dispatch, prompt save/reload, admin eval runner и focused booking regression. Предыдущие 2344 passed не заменяют gate нового кода; известные дефекты из побочного аудита проверяются отдельно перед rollout.

## Что требуется от владельца

1. Разобрать и принять границы этого пакета перед написанием кода.
2. Подтвердить актуальное содержимое ручного прайса и длительностей; исторические суммы не утверждены этим документом.
3. Если менять вход в запись — отдельно выбрать свободный текст или дополнительно одну контекстную кнопку. Рекомендация первого пакета: сохранить текущий вход, не смешивать смену источника знаний с UX-переделкой.

Следующая очередь после пакета: проверить необходимость legacy полей Router и упростить оставшееся соединение ответов по потребителям; затем отдельно UX записи/частота технического sync. Не объединять всё в большой рефакторинг.

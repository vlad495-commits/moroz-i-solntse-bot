# Дизайн обучающей HTML-карты Production Telegram V1

**Статус:** дизайн одобрен пользователем 2026-07-29

**Аудитория:** технический владелец проекта

**Результат:** самостоятельный файл `docs/production-v1-architecture.html`

## 1. Цель

Создать подробную интерактивную карту фактически реализованной Production
Telegram V1. Карта должна не только показывать компоненты, но и последовательно
провести технического владельца через систему: от входящего Telegram update до
ответа пользователю, фоновых задач, записи в YCLIENTS, админки и
эксплуатационного контура.

Критерий успеха: после прохождения карты владелец может своими словами объяснить,
из каких узлов состоит система, как между ними движутся данные, где хранится
состояние, какие механизмы защищают операции и что происходит при отказах.

## 2. Визуальный подход

За основу берётся язык прежней Foundation-карты из ветки
`codex/foundation-architecture-html`: спокойная техническая схема, автономный
HTML, кликабельные узлы и единая область подробностей.

Новая карта использует направленный граф модульного монолита вместо дерева одной
фазы. Основной экран одновременно показывает контейнеры, внутренние узлы,
хранилища, внешние интеграции и эксплуатационный периметр.

Чтобы подробная схема оставалась понятной, она дополняется режимом пошаговой
экскурсии. На каждом шаге один узел и его связи выделяются, остальные компоненты
приглушаются.

## 3. Компоновка

Карта состоит из следующих зон:

1. Внешний контур: клиент Telegram, Telegram Bot API, оператор и технический
   владелец.
2. Ingress: DNS/HTTPS, Caddy, webhook secret и маршруты `/telegram/webhook`,
   `/admin`, `/healthz`.
3. Runtime-процессы: `bot`, `admin`, `worker`, `scheduler`, `migrate`.
4. Приём сообщения: нормализация update, проверка возраста и дублей, privacy
   gate, durable inbox, per-chat buffer и постановка задачи.
5. Обработка: RabbitMQ consumer, per-chat serialization, scripts-first router,
   сценарии FAQ/записи/эскалации и единый результат обработки.
6. LLM security: input validation, PII masking, jailbreak/prompt-leak guards,
   primary/reserve gateway, output validation, один bounded retry и fallback.
7. Запись: booking state machine, PostgreSQL ownership, YCLIENTS adapter,
   create/get/reschedule/cancel и reconciliation неизвестного результата.
8. Доставка ответа: durable outbound, Telegram sender, классификация ошибок,
   retry и сохранение результата.
9. Фоновые задачи: scheduler jobs, напоминания, lifecycle checks, no-show,
   feedback-once, follow-up, retry и DLQ.
10. Данные: PostgreSQL, Redis, RabbitMQ и Alembic с детализацией основных
    таблиц, ключей и границ ответственности.
11. Админка: DB-сессии, TOTP-ready login, RBAC, CSRF, audit, диалоги,
    статистика, промпты, эвалы, логи, bot control и owner-only metrics.
12. Operations: Compose-контуры, health/readiness, метрики, алерты, backup,
    verify/restore, smoke/load/failure gates, deploy и app-only rollback.

## 4. Пошаговые экскурсии

Карта содержит кнопку `Начать разбор`, навигацию `Назад` / `Далее` и выбор
отдельного маршрута:

### 4.1. Путь Telegram-сообщения

Клиент → Telegram → Caddy → webhook → privacy gate → inbox → buffer → RabbitMQ
→ worker → router/scenario → LLM security → outbox → Telegram sender → клиент.

### 4.2. Запись через YCLIENTS

Намерение записи → booking state machine → локальный owner/key → чтение слотов
→ явное подтверждение → mutation → проверка внешнего состояния → локальный
checkpoint → сервисные уведомления.

### 4.3. Scheduler и уведомления

Durable scheduler job → publisher → RabbitMQ → worker handler → Telegram или
read-only YCLIENTS lifecycle check → retry/DLQ/эскалация.

### 4.4. Админка и контроль

HTTPS `/admin` → login/TOTP → DB session → RBAC/CSRF → выбранная операция →
audit → PostgreSQL/Redis/metrics.

### 4.5. Надёжность и выпуск

Alembic migration → Compose processes → health/readiness → metrics/alerts →
encrypted backup → smoke/load/failure evidence → immutable image rollback.

После завершения экскурсии карта возвращается к полному обзору.

## 5. Детали каждого узла

Выбор узла открывает единую панель со следующими полями:

- назначение простыми словами;
- роль в текущем потоке;
- входящие и исходящие данные;
- постоянное и временное состояние;
- гарантии и защитные проверки;
- поведение при сбое;
- связанные узлы;
- основные файлы реализации;
- статус: `реализовано`, `проверено на staging`,
  `требует production evidence` или `post-launch backlog`.

В карточках не показываются секреты, реальные токены, адрес сервера, персональные
данные и содержимое `.env`.

## 7. Граница реализованного

Карта показывает только фактически существующий Telegram V1 runtime.

Отдельно, приглушённо и без включения в рабочие потоки, отмечается post-launch
backlog:

- WhatsApp, Instagram, ВКонтакте и сайт;
- ЮKassa;
- голос и SpeechKit;
- полноценный UI управления записями;
- управление базой знаний из админки;
- рабочий UI эскалаций;
- массовые рассылки и реактивация;
- расширенная бизнес-аналитика и observability.

Эти узлы не должны выглядеть реализованными.

## 8. Технический формат

- один автономный HTML-файл без сервера и сборщика;
- CSS, SVG и JavaScript находятся внутри файла;
- внешние запросы и библиотеки отсутствуют;
- светлая и тёмная тема через системные настройки;
- доступные кнопки, видимый focus и управление клавиатурой;
- адаптивная компоновка без горизонтального переполнения на ширине 320 px;
- основной вид полезен без JavaScript, интерактивность улучшает разбор;
- анимация используется только для перехода между шагами и отключается через
  `prefers-reduced-motion`.

## 9. Проверка результата

Перед сдачей необходимо:

1. сверить узлы и связи с `План реализации.md`, фазовыми планами, Compose,
   миграциями и фактическим деревом `project/`;
2. проверить отсутствие узлов, которые существуют только в целевом ТЗ;
3. открыть standalone HTML и пройти все экскурсии;
4. проверить клики и клавиатурный выбор каждого узла;
5. проверить отсутствие JavaScript errors и несуществующих file paths;
6. визуально проверить широкую и узкую ширину, светлую и тёмную тему;
7. проверить отсутствие внешних запросов, секретов, placeholder-текста и
   горизонтального переполнения;
8. выполнить статическую проверку HTML-контрактов и `git diff --check`.

## 10. Критерий готовности

Технический владелец открывает один файл, запускает экскурсию, проходит основные
потоки системы и после этого понимает:

- какие процессы запущены и зачем;
- как проходит пользовательское сообщение;
- где и почему используются PostgreSQL, Redis и RabbitMQ;
- как устроены LLM security и YCLIENTS booking;
- как работают scheduler, уведомления и админка;
- какие гарантии уже проверены;
- почему staging готов к ручной приёмке, а production launch ещё заблокирован.

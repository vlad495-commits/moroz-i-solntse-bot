# Дизайн подробной HTML-схемы Production Telegram V1

**Статус:** дизайн одобрен пользователем 2026-07-29

**Аудитория:** технический владелец проекта

**Результат:** самостоятельный файл `docs/production-v1-architecture.html`

## 1. Цель

Создать подробную статичную схему фактически реализованной Production Telegram
V1. Схема должна последовательно провести технического владельца через систему:
от входящего Telegram update до ответа пользователю, фоновых задач, записи в
YCLIENTS, админки и эксплуатационного контура.

Критерий успеха: после прохождения карты владелец может своими словами объяснить,
из каких узлов состоит система, как между ними движутся данные, где хранится
состояние, какие механизмы защищают операции и что происходит при отказах.

## 2. Визуальный подход

За основу берётся последняя workflow-компоновка Foundation из ветки
`codex/foundation-architecture-html`: спокойная техническая схема, центральная
последовательность шагов, боковые хранилища и инфраструктурные зоны, соединённые
ортогональными подписанными стрелками.

Новая схема не содержит кликабельных узлов, раскрывающихся карточек, вкладок,
фильтров и пошаговых кнопок. Вся информация видна сразу и читается сверху вниз.
Каждый узел содержит короткое назначение прямо внутри блока, а более крупные
границы подписывают контейнер, модуль или контур.

## 3. Компоновка

Схема состоит из четырёх последовательно расположенных workflow-полотен и
сквозного нижнего фундамента.

### 3.1. Основной путь сообщения

Первое и главное полотно читается строго сверху вниз:

- клиент Telegram;
- Telegram Bot API;
- Caddy HTTPS ingress и webhook secret;
- процесс `bot`;
- нормализация update, проверка возраста и дедупликация;
- privacy gate и согласие;
- durable inbox;
- per-chat buffer;
- RabbitMQ task;
- процесс `worker` и per-chat serialization;
- scripts-first router и выбор сценария;
- LLM security pipeline или детерминированный сценарий;
- durable outbound;
- Telegram sender;
- ответ клиенту.

PostgreSQL, Redis, RabbitMQ и внешние провайдеры располагаются по сторонам
центральной цепочки. Стрелки подписывают, какие данные записываются или читаются.

### 3.2. Ветка записи через YCLIENTS

От узла сценариев вправо уходит отдельная читаемая цепочка:

booking state machine → PostgreSQL owner/key → чтение услуг/сотрудников/слотов →
явное подтверждение → create/reschedule/cancel → проверка внешнего состояния →
reconciliation неизвестного результата → локальный checkpoint → постановка
уведомлений.

### 3.3. Фоновый контур

Отдельное полотно показывает замкнутый operational flow:

PostgreSQL scheduler jobs → процесс `scheduler` → RabbitMQ → процесс `worker` →
reminder/no-show/feedback/lifecycle handler → Telegram или read-only YCLIENTS
check → retry → DLQ/эскалация.

### 3.4. Админка и эксплуатация

Четвёртое полотно объединяет:

- Caddy `/admin` → FastAPI `admin`;
- login/TOTP-ready → DB session → RBAC/CSRF;
- диалоги, статистику, промпты, эвалы, логи, bot control, audit и metrics;
- public `/healthz`, owner-only `/admin/metrics`, alerts;
- backup → verify → isolated restore;
- deploy → smoke/load/failure gates → immutable app-only rollback.

### 3.5. Общий фундамент

Внизу на всю ширину располагается реализованная платформа:

- Docker Compose и отдельные процессы `bot`, `admin`, `worker`, `scheduler`,
  `migrate`;
- общий пакет `src/moroz`;
- PostgreSQL, Redis, RabbitMQ + DLQ;
- Alembic `0001`–`0009`;
- safe logging, readiness/heartbeat, retry, graceful shutdown;
- тестовый контур и последний полный gate `919 passed`.

## 4. Порядок чтения

У каждого полотна есть явный номер и короткий заголовок. Основная нумерация узлов
ведёт владельца по системе без интерактивности:

1. принять сообщение;
2. безопасно и надёжно зафиксировать его;
3. выбрать сценарий;
4. получить или сформировать результат;
5. доставить ответ;
6. выполнить отложенные действия;
7. наблюдать и обслуживать систему.

Основной путь выделяется сплошной линией. Запись через YCLIENTS, фоновые задачи и
операционные связи используют свои типы линий и текстовые подписи. Легенда
объясняет все типы связей и статусы.

## 5. Содержание узлов

Каждый узел показывает информацию без клика:

- номер или роль в потоке;
- короткое техническое имя;
- назначение одной понятной строкой;
- контейнер или модуль, если это не очевидно;
- ключевую гарантию или поведение при сбое;
- статус: `реализовано`, `проверено на staging`,
  `требует production evidence` или `post-launch backlog`.

На самой схеме не показываются секреты, реальные токены, адрес сервера,
персональные данные и содержимое `.env`. Пути к основным исходным файлам
собираются в компактной справочной полосе под соответствующим полотном, чтобы не
перегружать каждый блок.

## 6. Статусы и фактическая готовность

В верхней части показывается актуальный срез:

- фазы 1–8 реализованы;
- последний полный Docker gate: `919 passed`;
- staging technical smoke: `6/6`;
- миграция staging: `0009_production_admin`;
- staging: `READY FOR MANUAL ACCEPTANCE`;
- production launch checklist: `0/14` формально подписанных пунктов.

Цвет не является единственным носителем статуса: каждый статус имеет текстовую
подпись и различимый маркер.

## 7. Граница реализованного

Карта показывает только фактически существующий Telegram V1 runtime.

Отдельно, приглушённо и без включения в рабочие потоки, отмечается post-launch
backlog:

- WhatsApp, Instagram, ВКонтакте и сайт;
- ЮKassa;
- голос и SpeechKit;
- полноценный UI управления записями;
- управление базой знаний из админки;
- рабочий UI эскалаций;
- массовые рассылки и реактивация;
- расширенная бизнес-аналитика и observability.

Эти узлы не должны выглядеть реализованными.

## 8. Технический формат

- один автономный HTML-файл без сервера и сборщика;
- CSS, SVG и минимальный JavaScript отрисовки адаптивных соединителей находятся
  внутри файла;
- внешние запросы и библиотеки отсутствуют;
- светлая и тёмная тема через системные настройки;
- семантические секции и текстовое описание связей для screen reader;
- адаптивная компоновка без горизонтального переполнения на ширине 320 px;
- на узкой ширине полотна перестраиваются в линейные вертикальные цепочки;
- анимация, клики, hover-details и изменяемое состояние отсутствуют.

## 9. Проверка результата

Перед сдачей необходимо:

1. сверить узлы и связи с `План реализации.md`, фазовыми планами, Compose,
   миграциями и фактическим деревом `project/`;
2. проверить отсутствие узлов, которые существуют только в целевом ТЗ;
3. открыть standalone HTML и последовательно прочитать все четыре полотна;
4. проверить порядок и подписи всех стрелок;
5. проверить отсутствие JavaScript errors и несуществующих file paths;
6. визуально проверить широкую и узкую ширину, светлую и тёмную тему;
7. проверить отсутствие внешних запросов, секретов, placeholder-текста и
   горизонтального переполнения;
8. выполнить статическую проверку HTML-контрактов и `git diff --check`.

## 10. Критерий готовности

Технический владелец открывает один файл, идёт сверху вниз по пронумерованным
узлам и после этого понимает:

- какие процессы запущены и зачем;
- как проходит пользовательское сообщение;
- где и почему используются PostgreSQL, Redis и RabbitMQ;
- как устроены LLM security и YCLIENTS booking;
- как работают scheduler, уведомления и админка;
- какие гарантии уже проверены;
- почему staging готов к ручной приёмке, а production launch ещё заблокирован.

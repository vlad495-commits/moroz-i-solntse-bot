# Новый тестовый аккаунт YCLIENTS — дизайн подключения

## Цель

Подготовить пустой новый аккаунт YCLIENTS как изолированный sandbox для доказательства реального Telegram → YCLIENTS booking flow. Аккаунт не используется заказчиком в production, не содержит реальных клиентов и не принимает коммерческие записи.

## Выбранный вариант

Используется минимальный тестовый каталог:

- один тестовый филиал;
- одна услуга `Тестовая услуга API`;
- один сотрудник `Тестовый мастер`;
- расписание со свободными слотами минимум на два разных будущих времени в пределах 14 дней.

Production-подобный каталог из нескольких услуг и сотрудников не создаётся: он не нужен для проверки API lifecycle и увеличивает объём ручной настройки.

## Границы доступа и данные

- В YCLIENTS используются только синтетические названия и фейковые клиентские данные.
- Пароли, Partner Token и User Token не публикуются в чате, Git, логах или evidence-файлах.
- API credentials сохраняются только во внешнем ignored `.env`.
- Пользователь самостоятельно проходит вход, CAPTCHA, подтверждение почты/телефона и 2FA, если YCLIENTS этого потребует.
- Автоматизация интерфейса не читает сохранённые пароли, cookies или browser storage.
- Сначала разрешены только настройка пустого тестового кабинета и GET-only проверки. Предыдущее разрешение на один sandbox lifecycle уже было израсходовано остановленной preflight-попыткой и не переносится на новый аккаунт.

## Поток настройки

1. В авторизованном кабинете создать минимальный филиал, услугу, сотрудника и расписание.
2. Получить company, service и staff IDs; привязать существующий Partner Token API-приложения проекта и выпустить новый User Token с правами этого тестового аккаунта. Все значения безопасно сохранить во внешнем `.env`.
3. Заполнить allowlists и `YCLIENTS_ENVIRONMENT_LABEL=sandbox` во внешнем `.env`.
4. Через Docker выполнить GET-only readiness: филиал, exact услуга, exact сотрудник, 14-дневное окно слотов и чтение записей.
5. При любом `401/403`, неожиданном envelope, duplicate/missing ID или отсутствии двух будущих слотов остановиться без POST/PUT/DELETE.
6. После успешного GET-only gate запросить отдельное явное разрешение на один lifecycle именно нового тестового аккаунта.
7. После разрешения выполнить один bounded flow с новым UUID и фейковыми данными: `create → get → reschedule → get → cancel → final get → reconciliation`.
8. Включение Telegram booking и scheduler в staging остаётся отдельным решением после успешного lifecycle.

## Fail-closed и cleanup

- Mutation не повторяется вслепую после timeout, connection drop или malformed response.
- При outcome unknown дальнейшие mutations запрещены; выполняется одна GET-only reconciliation и создаётся сигнал для ручной проверки.
- После definite post-create сбоя допустима только bounded cleanup-cancel по exact external ID/key и одна финальная reconciliation.
- Успешный результат требует ровно одну найденную тестовую запись и `active_matches=0` после отмены.
- Любая остаточная активная запись блокирует дальнейший rollout.

## Проверки и доказательства

- Все локальные тесты и проектные команды запускаются только через Docker Compose.
- До внешних mutation используются существующие unit/contract/integration/E2E mock gates.
- Внешний отчёт содержит только environment label, counts, этапы, exit code и санитизированные reconciliation-результаты.
- Токены, имена, телефоны, provider payload, external booking IDs и booking keys в отчёт не попадают.
- После логического шага обновляются `Дорожная карта.md`, `changelog.md` и создаётся локальный commit; push выполняется только по отдельному запросу.

## Критерии завершения этапа

- GET-only readiness нового аккаунта завершён exit `0`.
- Отдельно разрешённый lifecycle завершён полной цепочкой и bounded cleanup.
- Reconciliation доказывает одну отменённую тестовую запись и отсутствие активного остатка.
- Duplicate/replay, ownership, provider failure и scheduler/reminder regressions остаются зелёными.
- Только после этого новый sandbox может использоваться для ограниченного Telegram smoke-теста.

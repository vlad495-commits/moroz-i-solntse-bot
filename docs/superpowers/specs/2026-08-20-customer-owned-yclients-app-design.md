# Customer-owned YCLIENTS Production App Design

Дата: 2026-08-20  
Статус: одобрено владельцем проекта

## Цель

Подключить Telegram Production V1 к действующему филиалу заказчика через отдельное бесплатное непубличное приложение YCLIENTS, которым управляет заказчик. Текущее приложение разработчика сохраняется только для dev/test и не используется как production credential boundary.

## Решение

- Production-приложение создаётся в кабинете разработчика YCLIENTS, контролируемом заказчиком.
- Тип приложения — `Непубличное`; тип монетизации — `Бесплатное`.
- Приложение обслуживает один production-филиал и один комплект статических credentials, что совпадает с текущей single-tenant конфигурацией бота.
- Partner Token, User Token и `company_id` принадлежат production-контуру заказчика и хранятся только в server-only `.env`.
- Текущее приложение `Moroz i Solntse Telegram Bot` под аккаунтом разработчика остаётся dev/test и не переносится в production.
- Публичное marketplace-приложение и multi-tenant onboarding не создаются в этом релизе.

## Почему выбран этот вариант

Проект является индивидуальной системой одного бизнеса, а не самостоятельным SaaS-продуктом для множества компаний. Customer-owned credential boundary сохраняет контроль заказчика над бизнес-данными и отключением интеграции, не требует marketplace-модерации и не добавляет в текущий single-tenant runtime activation API, tenant registry и per-tenant secret storage.

Публичное приложение под аккаунтом разработчика станет правильным отдельным продуктовым решением только при повторном использовании интеграции несколькими независимыми компаниями. Тогда потребуются marketplace activation/deactivation flow, multi-tenant secrets, договорная поддержка и отдельная спецификация.

## Владение и роли

### Заказчик

- контролирует YCLIENTS-филиал, production-приложение и восстановление доступа к кабинету;
- подтверждает выдаваемые приложению права;
- определяет сотрудника, услугу и временное окно для синтетической проверки;
- может отозвать приложение и его доступ без изменения кода бота.

### Технический владелец

- помогает настроить приложение без получения пароля заказчика в чат или Git;
- переносит credentials только через согласованный безопасный канал прямо в server-only `.env`;
- выполняет read-only и отдельно разрешённый mutation smoke;
- поддерживает runbook ротации, отзыва и rollback.

### Бот

- использует `YCLIENTS_PARTNER_TOKEN`, `YCLIENTS_USER_TOKEN` и `YCLIENTS_COMPANY_ID` как единственный production binding;
- получает каталог, сотрудников, слоты и записи; создаёт, получает, переносит и отменяет только записи, которыми владеет по PostgreSQL и exact `moroz_booking_key`;
- не хранит пароль кабинета заказчика и не получает доступ ко всей клиентской базе.

## Целевой поток

```text
Клиент Telegram
    → бот/worker на нашем сервере
    → Partner Token + User Token production-приложения
    → API действующего филиала YCLIENTS заказчика
    → услуги / сотрудники / слоты / записи
    → локальная projection и scheduler
```

## Минимальные права

Финальная выдача сверяется с фактическими названиями в кабинете YCLIENTS. Базовый allowlist:

- `Журнал записи`: неограниченный доступ к истории расписания и записей; перенос записи.
- `Форма записи`: доступ к данным клиента внутри записи; создание нового клиента в записи; просмотр дополнительных полей записи; создание, изменение и удаление записей; изменение дополнительных полей, комментария и состава услуг.
- `Настройки`: доступ к разделам услуг и сотрудников без прав создания, удаления, финансов и управления пользователями.
- `Раздел «Обзор»`: просмотр списка записей.

Не выдаются права на клиентскую базу целиком, телефоны в списках, финансы, лояльность, склад, рассылки, пользователей, системные настройки и оплату. Если официальный endpoint требует дополнительное право, оно добавляется только после одного доказанного `403`, сверки с документацией и записи решения в changelog.

## Настройка филиала

- Создать дополнительное поле записи с кодом `moroz_booking_key`.
- Тип — текст; пользователь приложения может читать и изменять поле; поле не используется как видимый бизнес-реквизит.
- Сопоставление записей выполняется только по provider `external_id` и exact UUID в `moroz_booking_key`.
- Имя, телефон, услуга и время не используются как доказательство владения записью.

## Секреты и доступ

- Пароль, TOTP, Partner Token и User Token не передаются в чат, Git, документацию, changelog, screenshots или test output.
- Заказчик сам входит в YCLIENTS; технический владелец сопровождает настройку совместно либо получает values через утверждённый защищённый канал.
- Server-only `.env` сохраняет права доступа владельца и не копируется в локальную документацию.
- Любая возможная утечка token value требует ротации до следующего внешнего вызова.
- Staging первым получает production YCLIENTS credentials только для bounded acceptance; production получает их после успешного staging gate.

## Порядок приёмки

1. Проверить приложение, тип монетизации, филиал и выбранные права без вывода token values.
2. Проверить `company_id`, services, staff, slots, additional field и records-list только GET-запросами.
3. Запустить projection sync через штатный scheduler и подтвердить только counts/status/freshness без ПД.
4. Получить отдельное разрешение на mutation smoke.
5. Создать одну синтетическую запись на согласованную услугу и сотрудника, получить её, перенести, повторно получить и отменить.
6. Read-only reconciliation должен показать один exact match и ноль активных тестовых записей после отмены.
7. Неопределённый mutation outcome останавливает автоматизацию; blind retry и guessed cleanup запрещены.

## Ошибки и rollback

- `401/403` считается configuration/access failure и не повторяется автоматически.
- Недоступность каталога, records-list или `moroz_booking_key` оставляет YCLIENTS gate открытым; бот сохраняет FAQ и передачу записи администратору.
- При ошибке после переключения staging восстанавливается предыдущий server-only env snapshot и пересоздаются только app services; БД не откатывается.
- Отзыв приложения заказчиком немедленно прекращает новые YCLIENTS operations; локальная projection не считается актуальной.
- Отключение и ротация credentials описываются в onboarding-плане и не требуют удаления исторических записей проекта.

## Критерии готовности

- Production-приложение контролируется заказчиком, бесплатно и непублично.
- Выданы только утверждённые права; `Просматривать список записей` включено.
- `moroz_booking_key` существует с проверенными свойствами.
- Secrets находятся только в server-only env и не появляются в evidence.
- Read-only gate, projection scheduler и один разрешённый lifecycle smoke прошли.
- После cancel активных synthetic matches нет.
- Полный Docker gate, независимый review, staging acceptance, rollback и owner TOTP закрыты до production rollout.

## Вне scope

- Публикация в маркетплейсе YCLIENTS.
- Подключение нескольких компаний одним приложением.
- Автоматическая регистрация/активация tenants.
- Оплата подписки приложения через marketplace.
- Передача заказчику текущего dev/test-приложения.

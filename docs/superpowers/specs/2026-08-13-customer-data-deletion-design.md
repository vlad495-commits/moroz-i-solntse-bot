# Полное удаление локальных данных клиента — дизайн

**Дата:** 2026-08-13  
**Статус:** одобрено владельцем продукта с делегированием технических решений Codex  
**Источник:** сравнительный аудит решений бота Володи

## Цель

Дать владельцу безопасный способ безвозвратно удалить из активных хранилищ бота все локальные данные Telegram-клиента. Внешняя запись и карточка клиента в YCLIENTS не изменяются.

## Принятое решение

Реализовать один небольшой сервис удаления, вызываемый из существующей карточки диалога в админке. Не добавлять отдельную очередь, новую таблицу клиентов, фоновый процесс или универсальный privacy-фреймворк.

Операция удаляет данные из PostgreSQL и Redis, использует существующую блокировку обработки чата и сохраняет только обезличенный административный аудит.

## Пользовательский сценарий

1. Только пользователь админки с ролью `owner` видит опасную зону в карточке диалога.
2. После первого нажатия интерфейс показывает последствия операции.
3. Владелец вводит точную фразу `УДАЛИТЬ` и отправляет защищённую CSRF форму методом `POST`.
4. После успеха админка возвращает владельца к списку диалогов с нейтральным сообщением об удалении.
5. Следующее сообщение этого Telegram-пользователя считается новым обращением и снова проходит получение согласия.

Удаление через `GET`, JavaScript-only confirmation и доступ для роли `admin` запрещены.

## Граница данных

### PostgreSQL

Идентичность текущего Telegram-клиента определяется тремя согласованными значениями:

- `chat_id` как `BIGINT` для legacy-таблиц `messages` и `token_usage`;
- `chat_id` как строка и `channel = 'telegram'` для messaging-таблиц;
- `customer_id = str(chat_id)` для booking, scheduler и escalation-таблиц;
- фактические `user_id`, найденные в сообщениях и payload, для `processing_consents`.

Сервис держит явный манифест удаления. Он охватывает:

- `messages`, `token_usage`;
- `message_inbox`, `outbound_messages`;
- `task_outbox` только по известным структурированным JSON-полям `chat_id`, `user_id` или `customer_id`, без подстрочного поиска;
- `processing_consents`;
- `booking_events`, `bookings`, `booking_scenarios`;
- `scheduler_jobs`, `notification_feedback_requests`;
- `escalations`, `human_mode`;
- опциональную legacy-таблицу `security_incidents`, если она существует.

Общие prompt/eval/admin-таблицы не являются клиентскими и не удаляются. `admin_audit_events` не удаляется, но новая запись удаления не содержит клиентского идентификатора.

### Redis

Удаляются только известные ключи и элементы клиента:

- `chat:{chat_id}:messages`;
- `buffer:{chat_id}`;
- `lock:buffer:{chat_id}`;
- элемент `{chat_id}` из `buffer:deadlines`;
- `consent:state:telegram:{chat_id}:{user_id}` для найденных `user_id`;
- временная метка удаления.

Глобальные ключи, включая `bot:paused`, не затрагиваются. `SCAN` по всей Redis и удаление по широкому шаблону не используются.

## Порядок и конкурентность

1. Админка ставит Redis-метку `privacy:deleting:telegram:{chat_id}` с TTL 300 секунд.
2. Telegram webhook проверяет метку до consent flow и `MessageService.accept`. Во время удаления он отвечает HTTP 200, но не создаёт клиентские записи. Никакой новый текст не логируется.
3. Сервис открывает PostgreSQL-транзакцию и выполняет `pg_advisory_xact_lock(hashtextextended('telegram:' || chat_id, 0))` — тот же ключ, который использует worker для Telegram-чата.
4. После получения lock сервис собирает `user_id`, UUID сценариев и booking keys.
5. Пока транзакция и ingress-метка активны, сервис очищает Redis. Ошибка Redis прерывает операцию и откатывает SQL.
6. PostgreSQL удаляется в порядке зависимостей: события и задания, бронирования, сценарии, messaging-данные, согласия и legacy-история.
7. Перед commit сервис повторно считает связанные строки. Ненулевой остаток считается ошибкой и вызывает rollback.
8. В той же транзакции создаётся обезличенный audit event.
9. После commit снимается ingress-метка. Если снятие не удалось, TTL гарантированно освободит клиента не позднее пяти минут; данные при этом уже удалены.

Потеря Redis-контекста при последующей ошибке PostgreSQL допустима: постоянные данные остаются в БД, а временная память безопасно восстановится с нового диалога.

## Аудит

Событие имеет:

- `action = 'customer_data.delete'`;
- `object_type = 'customer_data'`;
- `object_id = NULL`;
- `before = NULL`;
- `after` только с каналом, итогом и количеством удалённых строк по категориям;
- существующие `actor_id`, время, IP и user-agent администратора.

В audit payload запрещены `chat_id`, `user_id`, username, имя, телефон, текст сообщений, payload входящего сообщения, YCLIENTS external ID и booking key.

## Ошибки и повтор

- Неверная подтверждающая фраза: HTTP 400, никаких изменений.
- Неверная роль или CSRF: HTTP 403 до Redis и БД.
- Ошибка Redis до SQL commit: SQL rollback, безопасная ошибка в интерфейсе.
- Ошибка PostgreSQL: rollback; очищенный Redis-контекст не восстанавливается.
- Повторный запрос: идемпотентно дочищает известные Redis-ключи и возвращает нейтральный результат `already_absent`; прежний идентификатор не попадает в аудит.
- Код операции не импортирует и не вызывает YCLIENTS adapter.

## Логи и резервные копии

Активная операция охватывает PostgreSQL и Redis. Код удаления не пишет клиентские идентификаторы или содержимое сообщений в новые application logs.

Существующие зашифрованные backup-архивы не переписываются выборочно. Они удаляются по утверждённому сроку хранения. Процедура восстановления обязана считать восстановленную БД изолированной и не вводить её в production без проверки актуальности удаления и privacy-review. До production launch срок хранения backup должен быть записан в runbook.

## Приёмочные критерии

- Owner может удалить клиента только через CSRF-protected POST и точную фразу `УДАЛИТЬ`.
- Admin не видит действие и получает 403 при прямом POST.
- Все строки явного манифеста и все известные Redis-ключи клиента исчезают.
- Параллельный webhook не создаёт новые клиентские строки во время операции.
- Audit event не содержит клиентских идентификаторов и контента.
- YCLIENTS не вызывается и внешняя запись остаётся неизменной.
- После удаления обычное сообщение получает consent flow.
- Повторная операция безопасна.
- Тесты выполняются только через Docker Compose.

## Не входит в эту задачу

- удаление или изменение данных в YCLIENTS;
- создание cross-channel профиля клиента;
- массовое удаление нескольких клиентов;
- пользовательская команда самоудаления в Telegram;
- отдельный сервис privacy jobs;
- переработка старых backup-архивов.

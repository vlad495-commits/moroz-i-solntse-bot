# Система управления проектом Moroz i Solntse Bot — design

**Дата:** 2026-08-20  
**Статус:** одобрено пользователем, вариант 2 — единый пульт управления  
**Область:** только структура проектной документации и правила координации; runtime, release candidate, staging, production и внешние интеграции не изменяются

## 1. Проблема

Проект вырос из ступенчатого шаблона LLM-бота в полноценную программу Telegram Production V1. При этом старые и новые документы продолжили одновременно описывать текущее состояние:

- `AGENTS.md` сохранил исходную ступень 1;
- `Дорожная карта.md` содержит ступень 3, текущий release candidate, дальнюю целевую архитектуру, завершённые отчёты и backlog;
- `План реализации.md` хранит статусы восьми production-фаз;
- `changelog.md` фиксирует каждое действие и визуально похож на источник статуса;
- аудит бота Володи породил отдельный набор продуктовых пробелов, но их связь с общей дорожной картой не закреплена одной таблицей.

Из-за этого несколько корректных документов дают разные ответы на вопрос «где проект сейчас». Основной дефект — не количество файлов, а отсутствие однозначного владельца каждого вопроса.

## 2. Цель

Сделать `Дорожная карта.md` единственным коротким пультом текущего состояния, а каждому остальному документу назначить одну неизменную роль. По одному экрану владелец должен понимать:

1. какой релиз сейчас готовится;
2. какая работа активна;
3. что уже доказано;
4. какие блокеры остаются;
5. что требуется от владельца;
6. какие задачи идут дальше и из какого источника они появились.

## 3. Не входит в задачу

- изменение продуктовых требований без отдельного решения владельца;
- изменение runtime-кода;
- review, push, merge или rollout текущего release candidate;
- перенос управления в Jira, Notion или другой внешний сервис;
- переписывание исторических фактов в changelog, Git или закрытых specs/plans;
- превращение Lucky Hair Studio в источник бизнес-правил Moroz i Solntse.

## 4. Текущее фактическое состояние

На момент проектирования текущий release candidate находится в ветке `codex/staging-update-2026-08-18`, локальный HEAD `e8efa47000b859e8bf700a291a539673f85c9800`.

Локально реализованы YCLIENTS suppression, outbound privacy fence и commit-pinned staging scheduler. Полный Docker gate прошёл `1258` тестов. Пять локальных коммитов ещё не опубликованы в PR №2; повторный независимый review, push, merge, staging rollout и серверная диагностика `yclients_http_status` не выполнены.

Это состояние должно быть отражено в новой дорожной карте как один release checkpoint, а не размазано по нескольким документам.

## 6. Целевая структура

### 6.1. Корневая дорожная карта

`Дорожная карта.md` должна помещать оперативную часть примерно в 1–2 экрана и иметь фиксированные разделы:

1. `Где мы сейчас` — название текущего релиза, ветка/commit, среда и дата сверки;
2. `Активная работа` — не более одной основной release-работы и явно разрешённых параллельных задач;
3. `Доказано` — последние релевантные тесты/review/runtime evidence;
4. `Блокеры` — только незакрытые условия;
5. `Что нужно от владельца` — конкретное решение или `ничего`;
6. `Дальше` — `Now / Next / Later`;
7. `Источники` — ссылки на ТЗ, release plan, текущую spec/plan, аудит Володи и launch checklist.

Текущая подробная дорожная карта сохраняется byte-for-byte в `docs/archive/roadmap-history-through-2026-08-20.md`. История не удаляется.

### 6.2. Статические документы

В начало `ТЗ и архитектура.md`, `План реализации.md`, `changelog.md` и `checklist.md` добавляется короткий role-banner: на какой вопрос отвечает файл, на какой не отвечает и где смотреть текущий статус.

`AGENTS.md` теряет устаревшие утверждения о текущей ступени. Он ссылается на дорожную карту как на единственный status source и сохраняет только рабочие ограничения: Docker-only, secrets, temp files, roadmap/changelog discipline и Git.

### 6.3. Руководство по управлению

Создаётся `docs/project/Система управления проектом.md` со следующими разделами:

- реестр и происхождение документов;
- иерархия источников истины;
- правила обновления;
- жизненный цикл идеи и задачи;
- release coordination;
- универсальная формула для следующих проектов;
- типовые ошибки и защита от них.

Этот файл описывает процесс, но не содержит текущий status и поэтому не конкурирует с дорожной картой.

## 7. Иерархия источников истины

| Вопрос | Источник |
|---|---|
| Где проект сейчас и что следующее? | `Дорожная карта.md` |
| Каким должен стать продукт? | `ТЗ и архитектура.md` |
| Что входит в Telegram Production V1? | `План реализации.md` |
| Что должна делать конкретная функция? | соответствующая spec |
| Как её реализовать и проверить? | соответствующий implementation plan |
| Почему принято значимое архитектурное решение? | ADR или раздел решения в одобренной spec |
| Что фактически сделано? | Git, тестовые evidence и `changelog.md` |
| Что можно взять у внешнего референса? | аудит; перенос начинается только после попадания кандидата в roadmap |
| Что реально развёрнуто? | runtime evidence, затем отражённый release checkpoint в roadmap |

Если два документа противоречат друг другу, вопрос решается владельцем соответствующего источника, а не выбором более удобной формулировки.

## 8. Связь с ботом Володи

Аудит Lucky Hair Studio остаётся датированным историческим снимком. В него добавляется отдельное приложение со статусами кандидатов:

### Реализовано или закрыто нашей более сильной реализацией

- consent-flow;
- полное удаление данных клиента;
- human handoff, очередь эскалаций и ответ администратора;
- журнал событий клиента;
- read-only центр записей и YCLIENTS reconciliation;
- YCLIENTS-каталог;
- надёжный buffer/inbox/outbox, LLM security, scheduler и operational foundation.

### Остаётся в продуктовой очереди

- детальный allowlisted trace одного запроса;
- постоянный профиль клиента и cross-channel identity;
- manual refresh и более точная атрибуция записей;
- версионированное управление знаниями;
- специализированные eval-представления/наборы;
- реактивация и ручные кампании;
- VK, Instagram и WhatsApp adapters.

### Исключено или не переносится

- голос/STT — исключён решением владельца;
- внутренняя БД расписаний вместо YCLIENTS;
- прямые provider-вызовы из admin;
- общий `env_file` для всех сервисов;
- монолитный worker Володи;
- перезапись `system.md` каталогом услуг.

Аудит не может самостоятельно создавать приоритет. Новый пункт из референса проходит цепочку: `audit → решение владельца → roadmap → spec → plan → implementation`.

## 9. Правила обновления

### Новая идея

1. Записать источник и ожидаемую пользу.
2. Если меняется продуктовая цель — обновить ТЗ или создать ADR/spec.
3. После решения владельца поставить инициативу в `Now / Next / Later` дорожной карты.
4. Только для выбранного `Now` создавать подробную spec и implementation plan.

### Начало задачи

1. Зафиксировать exact base branch/commit.
2. Создать изолированную ветку/worktree.
3. Сослаться из roadmap на одну активную spec/plan.
4. Явно записать, какие файлы и внешние среды задача не меняет.

### Завершение задачи

1. Получить тестовые и review evidence.
2. Сделать логический commit.
3. Добавить значимую запись в changelog.
4. Обновить статус roadmap.
5. Не объявлять deployed до runtime evidence.

### Релиз

1. Зафиксировать candidate commit/tag.
2. Пройти полный gate и независимый review.
3. Получить отдельное разрешение на push/merge/rollout, если оно требуется.
4. Сохранить rollback.
5. Проверить runtime и внешние интеграции.
6. Только после этого обновить roadmap как `развёрнуто`.

## 10. Универсальная формула

```text
Идея / референс
    → ТЗ: что и зачем
    → ADR или spec: почему выбран этот путь
    → Roadmap: когда и с каким приоритетом
    → Release plan: в какой выпуск входит
    → Implementation plan: как сделать
    → Код + тесты + review
    → Git/changelog: доказательство
    → Runtime evidence
    → Roadmap: фактический новый статус
```

Короткое правило: **один вопрос — один источник правды; один активный релиз — один зафиксированный candidate; новый статус появляется только после доказательства.**

## 11. Порядок внедрения

Документационная реорганизация не добавляется в непроверенный release candidate и не расширяет PR №2. Последовательность:

1. завершить независимый review текущего `e8efa47`;
2. исправить findings и повторить затронутые gates при необходимости;
3. опубликовать пять release-коммитов в PR №2;
4. проверить PR, получить разрешение, merge и выполнить staging rollout;
5. проверить scheduler/privacy и диагностировать read-only YCLIENTS status;
6. от зафиксированного post-release состояния создать `codex/project-governance-cleanup`;
7. выполнить реорганизацию документов отдельным небольшим PR/merge;
8. обновить текущий status уже по фактическому post-rollout evidence.

Так документация не описывает промежуточное состояние как завершённый релиз и не увеличивает scope runtime review.

## 12. Проверка результата

После реализации должны выполняться следующие контракты:

- `AGENTS.md` не содержит `Текущая ступень`;
- в корне существует ровно один документ, объявленный источником текущего статуса;
- дорожная карта содержит обязательные разделы и не содержит подробных исторических task reports;
- архив старой дорожной карты существует и сохраняет прежнее содержимое;
- все role-banner ссылаются на дорожную карту;
- все ссылки на ТЗ, master plan, аудит Володи, specs/plans и launch checklist разрешаются;
- аудит Володи явно разделяет `реализовано / очередь / не переносить`;
- Git diff не меняет runtime, migrations, Compose, prompt, secrets или deployment scripts;
- `git diff --check` и документные pytest-контракты проходят через Docker.

## 13. Критерий успеха для владельца

Владелец открывает только `Дорожная карта.md` и за одну минуту отвечает:

- что сейчас делается;
- насколько это готово;
- что мешает завершению;
- что требуется от него;
- какая следующая работа;
- где посмотреть подробности и происхождение решения.

# B2: оставшиеся дефекты выбора записи

Продолжение одобрено владельцем 2026-09-06 без согласования каждого пункта. Изменения локально в текущей ветке, без rollout.

## Неразрешённое предпочтение специалиста

Дата или время не означают отказ от ранее названного специалиста. В create проверять сохранённое предпочтение при каждом продолжении с выбранной услугой, используя существующий _resolve_staff_preference. Пока имя неизвестно или неоднозначно, сохранять дату/время, повторять уточнение и не вызывать list_slots. Явное «любой специалист» или однозначное имя разблокирует поиск. Новые признаки состояния и resolver не нужны.

## Четвёртая и следующие записи

Сохранить компактные три варианта на странице и добавить контекстные «Далее»/«Назад» только к выбору существующей записи. Не возвращать постоянное меню. В scenario хранить полный список собственных записей и смещение страницы; Router видит только текущие варианты с глобальными индексами. Текстовый choice и кнопки должны выбирать один и тот же видимый вариант. Смена страницы инвалидирует старые кнопки, не меняет запись у провайдера; подтверждение и ownership остаются обязательными.

Альтернативы: полный кнопочный список перегружает ответ; фильтрация по дате усложняет различение исходной и новой даты переноса. Короткие страницы используют существующие choices/callback и устраняют обрезание без второго поиска/LLM.

Проверки: минимум четыре будущих собственных записи; переход на следующую страницу, глобальный index 3 в routing context; выбор кнопкой и текстом, отмена/перенос только выбранной записи и ровно один раз; stale/чужие/out-of-range callbacks ничего не меняют; возврат назад работает. Сохранить совместимость старых callback action codes, новый код только добавить в конец. На существующих черновиках без смещения использовать 0.

Полный внешний каталог/чужие записи не открывать. Ограничения Telegram callback 64 bytes и MAX_CHOICE_INDEX учитывать явно. Backend тестируется в Docker с fake YCLIENTS; живой Telegram/LLM — отдельная приёмка.

# Telegram YCLIENTS Self-Booking Design

Дата: 2026-09-04
Статус: одобрено владельцем проекта

## Цель

Завершить уже реализованную интеграцию YCLIENTS пользовательским сценарием внутри Telegram: клиент выбирает услугу, специалиста и реальное свободное время, передаёт контакт, подтверждает запись, а затем может перенести или отменить только ту запись, которую создал через этого бота.

## Решение

Используется нативный пошаговый интерфейс Telegram:

- inline-кнопки для услуг, дат, специалистов, времени и подтверждений;
- стандартная reply-кнопка Telegram `Поделиться номером` для контакта;
- ручной ввод имени и телефона как запасной путь;
- PostgreSQL для состояния сценария;
- существующие `BookingService`, `BookingRepository` и `YclientsAdapter` для внешних операций;
- существующие durable inbox, task outbox и outbound delivery для надёжной обработки.

Mini App, новый frontend, новая очередь, новый storage и LLM tool calling не добавляются.

## Почему этот вариант

Нативный Telegram-сценарий не заставляет клиента переходить на внешний сайт, не требует отдельного web-интерфейса и сохраняет контроль над каждым изменяющим действием. LLM остаётся консультантом и маршрутизатором, но не выбирает provider ID, не формирует команды YCLIENTS и не выполняет mutations. Это уменьшает риск неправильной даты, услуги или отмены.

## Граница владения

- `customer_id` для Telegram равен устойчивому ID текущего приватного чата.
- Созданная ботом запись сохраняется локально вместе с `external_id` и exact UUID в поле YCLIENTS `moroz_booking_key`.
- В разделе `Мои записи` доступны только будущие активные записи этого `customer_id`, созданные ботом и присутствующие в локальной таблице `bookings`.
- Записи, созданные через сайт, администратора, другой канал или старый бот, не показываются и не изменяются.
- Перенос и отмена используют существующий `BookingIdentity(confirmed=True)` только после совпадения Telegram `customer_id` и локального владельца записи.

## Пользовательский сценарий создания записи

1. Явная фраза о записи или кнопка `Записаться` запускает детерминированный booking-flow до обращения к основной LLM.
2. Бот показывает актуальные услуги из `yclients_service_catalog`. В первом релизе одна запись содержит одну услугу.
3. Клиент выбирает `Любой специалист` либо конкретного доступного специалиста.
4. Бот запрашивает у YCLIENTS реальные слоты и показывает только даты, на которых есть свободное время, затем конкретные времена с указанием специалиста.
5. Бот предлагает стандартную кнопку `Поделиться номером`. Контакт принимается как доверенный Telegram-контакт только если `contact.user_id` совпадает с отправителем. Иначе используется валидируемый ручной ввод.
6. Имя берётся из переданного контакта; если оно отсутствует, бот отдельно просит имя.
7. Действующее согласие на обработку ПД проверяется по существующему durable processing consent. Контакт не запрашивается до этого согласия.
8. Перед mutation бот показывает резюме: услуга, специалист, дата, время, имя и маскированный телефон.
9. Только кнопка `Подтвердить запись` переводит сценарий в выполнение и вызывает существующий `BookingService`.
10. После успешного ответа YCLIENTS бот отправляет подтверждение и убирает временную reply-клавиатуру.

Одновременно у клиента может быть только один незавершённый booking-flow. Команда `Отменить действие` завершает только текущий черновик и не отменяет подтверждённую запись.

## Перенос и отмена

1. Фраза о переносе/отмене или кнопка `Мои записи` открывает список только собственных будущих активных записей.
2. Если запись одна, бот сразу показывает её карточку; если несколько — предлагает выбрать.
3. Для переноса повторно выбираются дата и свободный слот для той же услуги; смена услуги оформляется как новая запись через администратора и не входит в V1.
4. Для отмены показывается точная карточка записи и отдельная кнопка подтверждения.
5. Действует существующее правило: автоматическое изменение менее чем за три часа до визита не выполняется и передаётся администратору.
6. После успешного переноса или отмены локальный snapshot, события и scheduler-задачи обновляются существующим booking lifecycle.

## Архитектура выполнения

### Webhook

- продолжает проверять Telegram secret, private chat, privacy deletion fence и consent;
- принимает текст, callback и контакт;
- callback подтверждается Telegram сразу, но бизнес-действие выполняется асинхронно;
- contact/callback сохраняются в durable inbox с минимальным структурированным payload; task outbox содержит только ссылки на update, без телефона и имени.

### Worker

- перед основной LLM проверяет активный booking-flow или однозначный локальный booking intent;
- передаёт booking-сообщение в один `TelegramBookingCoordinator`;
- coordinator читает и обновляет существующие `booking_scenarios`, каталог и локальные записи;
- внешний вызов выполняется только через существующий `YclientsAdapter` внутри worker;
- ответ ставится в существующий ordered outbound с reply/inline markup.

Если активного booking-flow нет и локальный маршрут неоднозначен, сообщение проходит через обычный LLM pipeline. LLM может объяснить услуги, но не выполняет booking mutation.

## Состояние и конкурентность

- Состояние шагов хранится в `booking_scenarios.state`; Redis не является источником истины.
- Новый additive Alembic revision добавляет только необходимые индексы/ограничения для одного активного сценария на `customer_id`; отдельная таблица wizard-state не создаётся.
- Каждое Telegram update обрабатывается идемпотентно по существующему external update ID.
- Все переходы одного клиента выполняются под существующим PostgreSQL advisory lock `customer_lock_subject(customer_id)`.
- Callback содержит только короткое действие и ID сценария; выбранные provider ID проверяются по текущему серверному состоянию, а не считаются доверенными данными.

## Ошибки и безопасное поведение

- Устаревшая кнопка не выполняет действие и предлагает открыть актуальный шаг.
- Занятый слот приводит к повторному показу свежих вариантов без автоматического выбора.
- `401/403`, устаревший каталог или недоступный YCLIENTS останавливают запись; FAQ и консультации продолжают работать.
- Неопределённый результат POST/PUT/DELETE не повторяется. Сценарий получает `booking_outcome_unknown` и эскалацию администратору.
- Телефон и имя не выводятся в технические логи, callback data, idempotency keys и безопасные evidence.
- Существующие customer deletion и retention обязаны удалять новые booking interaction payloads и ПД без восстановления их из проекции YCLIENTS.

## Изменение системного промпта

После реализации промпт больше не говорит, что бот не видит расписание и не создаёт записи. Новая граница формулируется точно: бот может создать, перенести и отменить только запись, оформленную этим же Telegram-пользователем через бота; остальные случаи направляются администратору или в публичную онлайн-запись.

## Проверка

- unit: переходы coordinator, callback validation, контакт и ручной телефон;
- integration: PostgreSQL-сценарии, один активный flow, ownership, idempotency, privacy deletion и retention;
- webhook: callback/contact проходят durable ingress и не попадают напрямую в LLM;
- worker E2E с fake transport: создание, занятый слот, перенос, отмена, late-change и unknown outcome;
- regression: существующие booking, messaging, consent, deletion, scheduler и admin-наборы;
- полный Docker gate, единственная Alembic head, Compose config, compile и независимое review;
- staging: сначала customer-owned read-only acceptance, затем одна отдельно разрешённая цепочка create/get/reschedule/get/cancel и ручная Telegram-приёмка.

## Критерии готовности

- клиент завершает создание записи внутри Telegram без внешней ссылки;
- все показанные услуги и слоты получены из актуального YCLIENTS;
- mutation выполняется только после явного подтверждения;
- `Мои записи`, перенос и отмена не открывают чужие или созданные вне бота записи;
- повтор update/callback не создаёт вторую операцию;
- unknown outcome не повторяется и создаёт эскалацию;
- ПД не появляются в логах и корректно удаляются;
- customer-owned YCLIENTS acceptance и production read-only smoke завершены.

## Вне scope

- Telegram Mini App;
- несколько филиалов;
- несколько услуг в одной записи;
- управление записями, созданными вне этого бота;
- смена услуги при переносе;
- оплата и ЮKassa;
- свободное LLM tool calling к YCLIENTS.

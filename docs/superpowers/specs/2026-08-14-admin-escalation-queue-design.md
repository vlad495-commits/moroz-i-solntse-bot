# Очередь эскалаций в админке — дизайн

## Цель

Дать собственнику и администраторам один рабочий экран для обращений, где бот передал диалог человеку: увидеть причину, открыть диалог и безопасно вернуть управление боту после решения вопроса.

## Границы

Используем существующие таблицы `escalations`, `human_mode`, `admin_audit_events` и существующую карточку диалога. Новых таблиц, зависимостей, фоновых процессов, Telegram-сообщений и вызовов YCLIENTS нет.

Не входят в эту работу: назначение ответственного, внутренние комментарии, SLA, уведомления сотрудникам, массовые операции и полноценный helpdesk.

## Доступ и интерфейс

- `owner` и `admin` видят в боковом меню раздел «Эскалации».
- `GET /escalations` показывает открытые обращения от новых к старым.
- Строка содержит время, идентификатор клиента, безопасную русскую подпись причины, источник, статус human mode и ссылку на существующий диалог.
- Raw `payload`, неизвестный `reason_code` и другие внутренние поля в HTML не передаются. Неизвестная причина отображается как «Требуется помощь администратора».
- Для каждого обращения доступна CSRF-защищённая кнопка «Закрыть и вернуть бота».

## Закрытие обращения

`POST /escalations/{escalation_id}/resolve` работает в одной PostgreSQL-транзакции:

1. Блокирует строку эскалации через `SELECT ... FOR UPDATE`.
2. Если строка уже закрыта, возвращает успешный идемпотентный результат без повторного изменения.
3. Переводит выбранную эскалацию в `resolved` и задаёт `resolved_at = now()`.
4. Проверяет, остались ли у этого клиента другие открытые эскалации.
5. Выключает `human_mode` только если открытых эскалаций больше нет. Новая или параллельная открытая эскалация сохраняет управление за человеком.
6. Пишет `admin_audit_events` с действием `escalation.resolve`, идентификатором эскалации и безопасными статусами без customer ID, payload или текста диалога.

После успеха выполняется redirect обратно в очередь. Неизвестный UUID даёт `404`, нарушение CSRF — существующий безопасный отказ, ошибка БД не оставляет частично закрытого состояния.

## Компоненты

- `project/admin/escalation_routes.py` — GET/POST маршруты и проверка ролей/CSRF.
- `project/admin/database.py` — bounded read-модель открытых эскалаций и транзакция закрытия.
- `project/admin/customer_events.py` — переиспользуемая allowlist-нормализация причины; второго словаря подписей не создаём.
- `project/admin/templates/escalations.html` — серверный HTML без JavaScript.
- `project/admin/templates/base.html` и существующий CSS — пункт меню и минимальные стили.

## Проверки

- Unit: известные и неизвестные причины нормализуются без утечки raw значений.
- Integration: сортировка и изоляция полей; атомарное закрытие; идемпотентный повтор; human mode выключается только после последней открытой эскалации; аудит не содержит клиентских данных.
- E2E admin: `owner` и `admin` видят очередь и могут закрыть обращение; anonymous получает существующий auth redirect; неверный CSRF блокируется; неизвестная эскалация даёт `404`; HTML экранируется.
- Финальный gate выполняется только через Docker Compose, затем независимый review Critical/Important.

## Критерии готовности

- Оба административных роли могут обработать открытую эскалацию из интерфейса.
- Закрытие одной из нескольких эскалаций не возвращает бота преждевременно.
- Повторное закрытие безопасно.
- Raw payload, произвольные reason/source и клиентский идентификатор не попадают в новый аудит.
- Существующие диалоги, событийный журнал, удаление данных, Telegram и YCLIENTS не ломаются.

# Доказательный аудит фоновых процессов и проект интеграции ЮKassa

Дата первого прохода: 2026-08-28.

## 1. Executive summary

Текущий production scope менять нельзя: активна Task 6 pre-YCLIENTS release, а первая production-версия по действующему ТЗ принимает оплату в центре. ЮKassa должна стать отдельной инициативой после решения владельца, закрытия YCLIENTS acceptance и выпуска текущего релиза. Доказательства: `Дорожная карта.md:28-37,50-51,70-72,98-116`, `docs/superpowers/plans/2026-08-28-pre-yclients-release-completion.md:410-489`, `ТЗ и архитектура.md:376-397`.

Что уже работает локально:

- Postgres-backed scheduler, отдельные `scheduler` и `worker`, RabbitMQ, durable queue/DLQ, retry, transactional outbox и идемпотентные ключи;
- подтверждение записи, напоминание за день, в 09:00 Москвы, за час и проверка результата визита;
- слияние утреннего и часового напоминаний в пределах 30 минут;
- инвалидирование старых задач после переноса или отмены;
- ограниченный опрос результата визита и постановка feedback-задачи после `completed`;
- единственность feedback-запроса на клиента и эскалация оценки `<= 3` на уровне сервиса.

Что опасно считать готовым:

1. Scheduler выбирает только `pending`-задачи. Если процесс погиб после перевода строки в `claimed`, но до публикации в RabbitMQ, автоматического возврата просроченного claim в `pending` не найдено. Задача может зависнуть навсегда (`project/src/moroz/notifications/repository.py:41-77,92-103`).
2. При временной ошибке YCLIENTS worker использует короткую очередь retry `1/5/30` секунд и затем DLQ. Длинные lifecycle-повторы `+15 минут/+2 часа/+24 часа` создаются только когда YCLIENTS успешно ответил статусом `confirmed`; ошибка API сама такой повтор не ставит (`project/src/moroz/notifications/lifecycle.py:12-16,61-93`, `project/src/moroz/common/queue.py:20-29,311-367`). Это не полностью выполняет требование о bounded retry с уведомлением персонала при технической неопределенности.
3. Feedback — не законченная пользовательская цепочка: нет Telegram callback/parser оценки, комментария, положительного сценария со ссылкой на Яндекс Карты и стоп-гейтов по ответу/отписке/human mode. Тест напрямую вызывает сервисный метод и поэтому не доказывает E2E-путь (`project/tests/e2e/notifications/test_feedback.py:108-193`).
4. Отдельное рекламное согласие не сохраняется. UI позволяет отметить новости, но `Done` записывает только processing consent; схема БД содержит лишь `processing_consents` (`project/llm/webhook.py:238-357`, `project/migrations/versions/0003_processing_consents.py:13-30`). Утверждение обратного в старом аудите является document drift (`docs/audits/Аудит решений бота Володи 2026-08-13.md:266-273`).
5. Реактивации и платежного runtime-кода нет. Команда поиска нашла слово reactivation только в тесте HTML-архитектуры, а payment — в том же архитектурном тесте и общем router, не в платежном модуле.

## 3. Verdict: feedback и reactivation

### Feedback — реализовано частично

Готова надежная половина «completed → единственная отложенная задача → исходящее сообщение» и сервис низкой оценки. Не готовы:

- прием оценки из Telegram и привязка ответа к ожидающему feedback;
- optional comment;
- положительная ветка со ссылкой на Яндекс Карты, отправляемой один раз;
- закрытие цепочки после любого ответа;
- запрет отправки после unsubscribe и human mode;
- явный статус feedback (`scheduled/sent/answered/suppressed/failed`) и repair для terminal failure;
- настоящий E2E от входящего Telegram update до escalation/human mode.

До закрытия этих пунктов фраза «сбор отзывов готов» неверна. Корректная формулировка: «планирование feedback и low-rating service готовы локально; пользовательский feedback flow не закончен».

### Reactivation — заблокировано внешней зависимостью или решением владельца

Это не «частично работающая» функция: runtime-кода нет. Статус «заблокировано» выбран потому, что владелец уже зафиксировал сознательную отсрочку до отдельного consent/unsubscribe, а не потому, что команда случайно не дописала модуль. Processing consent из `0003_processing_consents.py` разрешает обслуживание и хранение данных, но не рекламу.

Перед реактивацией нужны отдельные сущности примерно такого уровня:

- `marketing_consents(identity, purpose, version, granted_at, revoked_at, source)`;
- `marketing_suppressions(identity, reason, created_at)`;
- `reactivation_campaigns` и `reactivation_deliveries` с уникальным ключом клиента/кампании/шага;
- серверный расчет последнего completed visit и содержательного входящего диалога;
- send-time gates: consent active, no suppression, no new booking, no recent meaningful reply, no human mode, customer not deleted;
- один основной контакт и максимум один follow-up через 5 дней; следующая кампания не раньше 90 дней.

## 5. Gap analysis и целевой проект ЮKassa

### 5.1 Текущий gap

В runtime отсутствуют:

- payment/refund модели и миграции;
- provider port/adapter и test shop configuration;
- backend create-payment use case;
- Telegram кнопка с `confirmation_url`;
- HTTPS webhook inbox и worker;
- API verification и state machine;
- admin read model, incident queue, аудит и метрики;
- receipt/54-ФЗ решение;
- contract, replay и crash-recovery тесты.

ТЗ сейчас только проектирует будущий модуль и явно исключает его из первого Telegram production (`ТЗ и архитектура.md:376-397,548-563,620,1003,1369`).

### 5.2 Официальные ограничения, на которых строится проект

- Платеж создается backend-запросом с аутентификацией, `Idempotence-Key`, суммой и сценарием; `confirmation_url` приходит в payment object. Для простого одностадийного сценария используется `capture=true`: [процесс платежа ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).
- `return_url` используется и при успехе, и при ошибке, поэтому не доказывает оплату. Источник истины — server-to-server webhook/API GET: [процесс платежа ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).
- ЮKassa ожидает HTTP 200; при другом ответе повторяет доставку до 24 часов. Подлинность предлагают проверять по текущему статусу объекта или IP. Официальной webhook-подписи на этой странице нет: [входящие уведомления](https://yookassa.ru/developers/using-api/webhooks).
- Идемпотентный ключ применяется к POST/DELETE, должен сохраняться для повтора одной операции; UUID v4 рекомендован: [формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format).
- `waiting_for_capture` нужен для двухстадийной оплаты; `succeeded` и `canceled` финальны. Отменить можно только hold, а успешный платеж требует refund: [процесс платежа](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process), [возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds).
- 54-ФЗ требует отдельного выбора кассового решения и данных чека. `vat_code`, `payment_subject`, `payment_mode` нельзя угадывать: [решения по 54-ФЗ](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/basics), [справочник значений](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/parameters-values).

### 5.3 Рекомендуемый сценарий

До другого решения владельца рекомендовать **опциональную одностадийную оплату (`capture=true`) после созданной записи**. Причины: запись по текущему ТЗ действительна без оплаты; бизнес-правил capture/cancel нет; двухстадийный hold создает финансовые дедлайны и права, которых продукт пока не определил.

Поток:

1. Backend принимает только локальный `booking_key`, загружает существующую запись, услугу и актуальную цену из серверных источников.
2. В транзакции создается local payment attempt со стабильным create idempotency key. Сумма, RUB и booking/client берутся с сервера; Telegram callback не содержит доверенной суммы.
3. Adapter делает `POST /v3/payments` с `capture=true`, redirect confirmation, минимальной metadata (`local_payment_id`, `booking_key`) и данными чека только после бухгалтерского решения.
4. `yookassa_payment_id`, provider status и `confirmation_url` сохраняются; бот отправляет кнопку «Оплатить» через существующий outbox.
5. Return page показывает «Проверяем статус» и никогда не помечает запись оплаченной.
6. HTTPS endpoint валидирует форму/размер, фиксирует событие в webhook inbox и только после commit отвечает 200. Worker получает текущий объект через API ЮKassa; IP allowlist — дополнительный слой, список берется из актуальной официальной документации/конфига, а не прошивается навечно.
7. Worker сверяет provider payment ID, local payment ID/booking key, сумму и валюту. Любое расхождение → security incident + admin task; booking не меняется.
8. Состояние обновляется монотонно и идемпотентно; поздний `pending` после `succeeded` не откатывает статус, потому что применяется текущий API object.
9. На `succeeded` один раз создается доменное событие/outbox «payment confirmed». `canceled` только фиксируется и предлагает клиенту повторить оплату; запись остается действующей. `waiting_for_capture` в выбранном одностадийном режиме считается configuration drift: сохранить, не capture автоматически, alert finance/admin.
10. Неизвестный payment/refund фиксируется в quarantine/inbox, создает admin task и не подтверждает booking.

### 5.4 Модель данных

`payments`:

- `id UUID PK`, `booking_key UUID FK`, `customer_id`/client identity;
- `provider='yookassa'`, `provider_payment_id UNIQUE NULLABLE`;
- `status`: `creating | pending | waiting_for_capture | succeeded | canceled | creation_failed | inconsistent`;
- `amount NUMERIC(12,2)`, `currency CHAR(3)`, `capture_mode`;
- `create_idempotency_key UNIQUE`, `confirmation_url` (не логировать, хранить только пока нужна);
- `provider_created_at`, `expires_at`, `succeeded_at`, `canceled_at`, `created_at`, `updated_at`;
- минимальная `metadata JSONB` без телефона, email, имени и секретов;
- snapshot услуги/цены для аудита, если это разрешит owner/accounting.

`payment_webhook_inbox`:

- сырой payload хранить ограниченно и с редактированием PII;
- `event`, `object_type`, `provider_object_id`, `payload_hash`, receive/process timestamps;
- уникальность `(provider, event, provider_object_id)`; для refund object ID — отдельный ID возврата;
- статусы `received | verified | applied | ignored_duplicate | incident | failed` и bounded retry.

`payment_status_history` — append-only old/new status, source, correlation ID, actor, timestamps. Будущий `refund_requests` проектировать отдельно; сейчас refund API не вызывается.

Разрешенные payment-переходы:

```text
creating -> pending | waiting_for_capture | succeeded | canceled | creation_failed
pending  -> waiting_for_capture | succeeded | canceled
waiting_for_capture -> succeeded | canceled
succeeded -> terminal
canceled  -> terminal
```

`inconsistent` — локальная защитная блокировка, а не provider status. Переход назад запрещен. Если webhook пришел не по порядку, API GET определяет фактическое текущее состояние.

### 5.5 Идемпотентность, падения и безопасность

- Ключ создания генерируется один раз на local payment attempt и повторно используется при сетевом retry. Новый ключ означает осознанно новый attempt.
- После неоднозначного ответа нельзя автоматически создать второй платеж новым ключом. После окна идемпотентности — admin reconciliation.
- Ключ refund в будущем создается на `refund_request_id`, а не на HTTP-попытку.
- Webhook handler не делает финансовые действия; он durable-принимает событие. Worker повторяем, а доменные эффекты защищены unique event/outbox keys.
- `shopId` и secret key — только env/secret storage. Секрет, Authorization, confirmation URL и receipt contact не попадают в логи. В логах: correlation ID, local payment ID, provider payment ID, booking key, event/status и error code.
- Endpoint только HTTPS. Rate/size limits, schema validation, current-object GET и optional IP allowlist. Никакой придуманной подписи.
- Метрики: create success/error/latency, webhook received/duplicate/invalid/verification failure/lag, payments per state, inconsistent/unknown, DLQ, stuck processing, time to succeeded. Алерты — unknown payment, mismatch, terminal regression, waiting_for_capture в one-stage, webhook backlog/DLQ.

### 5.6 Чеки и 54-ФЗ — отдельный бизнес-бухгалтерский блок

До кода бухгалтер/владелец должны зафиксировать:

- кто формирует чек: «Чеки от ЮKassa» или сторонняя онлайн-касса;
- юридическое лицо/ИП, систему налогообложения и применимость НДС;
- `vat_code` для каждой услуги;
- `payment_subject` (например, `service` — только после подтверждения бухгалтером);
- `payment_mode`: для предоплаты и окончательного расчета значения различаются; их нельзя выбрать технически без бизнес-сценария;
- состав `receipt.items`, quantity/measure и описание услуги;
- источник разрешенного email/телефона для доставки чека;
- чек зачета предоплаты и чек возврата, если выбранный сценарий этого требует.

### 5.7 Возвраты — безопасный текущий вариант

До утверждения политики: бот и backend только создают admin task с payment/booking context. Финансовый сотрудник проверяет платеж и вручную делает полный/частичный возврат в кабинете ЮKassa; результат приходит webhook `refund.succeeded` и отражается локально. Бот не вызывает refund API.

Варианты для будущего решения владельца:

1. **Ручной в кабинете ЮKassa** — рекомендуемый старт: минимальный риск, но больше ручной работы.
2. **Через нашу админку после подтверждения** — role + re-auth/confirm + reason + idempotency + audit; удобнее, но это финансовая функция высокого риска.
3. **Автоматический по правилам** — пока не рекомендован: требует утвержденных условий отмены/no-show/переноса, бухгалтерии, fraud controls и operational rollback.

Запрещено до отдельного решения: auto-refund, штраф no-show, удержание предоплаты, перенос денег между booking.

## 8. План реализации маленькими вертикальными срезами

План активируется только после решений владельца и отдельного approval.

### Slice 0. Решения и контракт

- Зафиксировать decision packet, ADR, 54-ФЗ и one/two-stage mode.
- Тест/приемка: review checklist без `TBD` по десяти блокирующим вопросам.

### Slice 1. Payment state machine и БД

- Миграции `payments`, `payment_webhook_inbox`, `payment_status_history`, индексы/constraints.
- Pure state transition policy и repository.
- Тесты: разрешенные/запрещенные переходы, money precision, unique idempotency/provider IDs, rollback.
- Приемка: миграция up/down в Docker; повтор события не меняет состояние второй раз.

### Slice 2. Создание test payment и кнопка

- Provider port + mock/contract adapter; server-derived booking/service/amount; stable key; `capture` по ADR.
- Сохранение provider ID/status/URL и отправка кнопки через outbox.
- Тесты: retry same key, timeout/ambiguous response, canceled/error, tampered Telegram amount ignored, no booking/no price denied.
- Приемка: в test shop создается один payment на один attempt; секреты/PII отсутствуют в логах.

### Slice 3. Durable webhook intake и verification worker

- HTTPS inbox endpoint, schema/size/IP controls, commit-before-200, API GET verification.
- Тесты: official-like contract payloads, duplicate/replay/out-of-order/delay, invalid JSON, unknown payment, wrong amount/currency/booking metadata, provider outage, crash after inbox commit and after domain commit.
- Приемка: повторы не дают повторного booking/outbox effect; mismatch только incident/admin task.

### Slice 4. Клиентский статус и recovery

- Return/status page «проверяем», команда/кнопка повторной проверки, canceled retry как новый явный attempt.
- Reconciliation job для pending/stuck и admin alert.
- Тесты: return before webhook, webhook before return, lost webhook, worker restart, stale pending.
- Приемка: return URL никогда сам не подтверждает payment; API reconciliation восстанавливает состояние.

### Slice 5. Read-only admin и observability

- Payment list/detail/history, фильтры, incident/admin tasks; роли просмотра; correlation/audit/metrics.
- Тесты RBAC, отсутствие secret/receipt contacts в UI/logs, metrics and alert thresholds.
- Приемка: только уполномоченная роль видит финансовые детали; финансовых кнопок еще нет.

### Slice 6. Чеки

- Реализовать только утвержденный бухгалтерией receipt flow.
- Contract tests по tax/VAT/subject/mode/contact и тестовому магазину.
- Приемка: тестовые чеки формируются выбранной кассой; бухгалтер подтверждает реквизиты и события.

### Slice 7. Refund visibility, без автоматизации

- Принимать/проверять `refund.succeeded`, хранить refund и показывать аудит; manual admin task остается процессом возврата.
- Тесты duplicate refund webhook, partial/multiple refunds, mismatch/unknown refund.
- Приемка: система отражает ручной возврат, но ни один клиентский или scheduler event не вызывает деньги наружу.

Будущая кнопка refund в админке или автоматизация — новый ADR и отдельный релиз, а не расширение этого плана.

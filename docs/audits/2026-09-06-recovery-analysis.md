Дата: 2026-09-06. Статус: восстановительные исправления реализованы в `codex/recovery-acceptance`; focused/live gates и полный Docker suite пройдены (2410 passed). ## Что требуется получить

Клиент понимает, с каким центром общается; новый клиент проходит обязательное согласие и независимо выбирает рекламу; повторный вход не сбрасывает этот выбор. LLM отвечает по ручной базе знаний, сохраняет тему и принимает уточнения в произвольном порядке. Код проверяет реальные услуги, слоты, владельца записи и согласия; внешняя операция возможна только после подтверждения. При отказе компонента клиент получает честное объяснение, а оператор — различимую причину.

Ни меню, ни количество тестов, ни число healthy-контейнеров не являются самостоятельной целью. Цель — доказуемая работа этих пользовательских сценариев на конкретной версии.

## Почему сбой прошёл проверки

1. Тест test_openai_receives_response_format_and_usage_keeps_purpose проверяет передачу словаря фальшивому клиенту. Он не проверяет принятие схемы сервером API.
2. test_router_path_counts прямо ограничен подсчётом вызовов; Router получает заранее сформированный JSON. Это полезная проверка проводки, но не живой классификации.
3. В unified evidence явно исключены live/paid проверки. Следовательно, статус выпуска подтверждал инфраструктуру и кодовые контракты, но не полную пользовательскую готовность. Запрет live не требовалось обходить; требовалось оставить приёмку незавершённой.
4. SDKProvider превращает HTTP-ошибки в безопасные классы без сохранения диагностической категории. Pipeline маскирует технический отказ фразой о непонятном запросе. Оператору трудно отличить инфраструктуру от смысла сообщения.
5. В ручном отчёте /start был назван OK без полного первого входа; пункты 9 и 10 объединены по одному emergency-запросу. Эти результаты нужно сузить до реально проверенного.

## Конкретный порядок работ

### 1. Один восстановительный пакет на текущей базе

- Зафиксировать базовый SHA и границы; отдельная codex/* ветка от актуального main. Старые worktree не продолжать автоматически.
- В messaging/router.py убрать uniqueItems из provider-схемы; оставить локальную проверку дублей и прочую валидацию. Проверить остальные фактически используемые форматы запросов в одном проходе: Router, Security, Answer, Validator, Compact. Не менять SDK, модель и архитектуру без выявленного дефекта.
- В security/llm_gateway.py и pipeline.py сохранить только безопасные категории отказа (например invalid_schema, authentication, rate_limit, timeout, invalid_output), purpose и HTTP status. Не писать сырые тела ошибок, ключи и сообщения клиентов. Использовать существующий журнал; отдельную систему мониторинга не строить.
- Заменить router fallback на честное техническое сообщение с проверенным публичным контактом. Убрать обещание «передам администратору», если передача этим путём не выполняется. Не обходить подтверждение внешних операций.
- В config.py восстановить содержательное представление центра; согласовать текст по прежнему приветствию и текущим реальным возможностям, без постоянного меню. Согласия не сбрасывать. Код их показа менять только при доказанном нарушении.
- Убрать из текущих LLM-инструкций только явно устаревшие указания: например каталоговый mode=catalog_browse при удалённом браузере каталога; проверить все потребители перед удалением. В system.md исправить ложную служебную пометку «на staging не развёрнут». Не переписывать базу цен и медицинские описания в пакете восстановления.

Результат этапа: один обозримый diff; список исправленных причин и явных UX-изменений. Изменения состояния БД, новая миграция и новый framework не требуются по имеющимся данным.

### 2. Дешёвые проверки до выкладки

- Docker-регрессии на изменённые контракты: несовместимая схема, локальная проверка дублей, технический fallback, отсутствие внешней операции при отказе Router, неизменность согласий и draft.
- Небольшой live smoke кандидата через реальные SDK/config и SecurityPipeline: FAQ с ценой, контекстный вопрос, контакт, запрос записи, mixed price+booking. Для dispatch использовать изолированное тестовое окружение без реальной записи. Отдельно принудительно вызвать путь Compact на длинном синтетическом контексте и Validator. Не ограничиваться успешным отдельным Router-запросом.
- Плановый предел: до 12 синтетических входов, по одному проходу; повторять только изменившийся/упавший случай. Если выявлена общая ошибка API, остановить остальные вызовы и устранить общую причину. Массовые платные evals в этот пакет не входят; live-вызовы имеют стоимость и выполняются в рамках отдельно согласованного исполнения.
- После focused и live gates — один полный Docker suite финального кандидата. Повтор полного suite только после затрагивающих его исправлений.
- Перед suite поправить связанный хвост прошлой уборки: test_full_project_architecture_visual.py всё ещё ссылается на корневой HTML, mount которого удалён. Это отдельная документная регрессия, не причина Telegram fallback; предыдущие 10 passed её не покрывали.

### 3. Выкладка одного кандидата и ручная приёмка

- После согласования rollout — immutable images, rollback, проверка exact SHA/config/prompt; инфраструктурная проверка и пользовательский прогон имеют отдельные результаты.
- Использовать существующий «План ручного тестирования.md», а не создавать ещё один checklist. Пройти все 18 сценариев и админку; найденный независимый дефект не отменяет остальные безопасные проверки. Останавливать только зависимые или небезопасные сценарии с точной причиной.
- Добавить различение входов: новый аккаунт без processing consent; новый аккаунт с processing и без рекламы; новый с явно выбранной рекламой; повторный /start; отказ от рекламы через /marketing. Существующие пользовательские согласия не удалять для теста. Для недоступных комбинаций использовать Docker integration + отметить отсутствие живой проверки, не ставить OK.
- Новый аккаунт видит форму; без обязательного согласия текст не передаётся LLM; реклама необязательна; после согласия приходит представление центра. Повторный старт не меняет рекламный выбор.
- Зафиксировать результаты, связанные сообщения и время, admin evidence, свежие безопасные логи и расходы. Проверку паузы выполнить в согласованное окно и вернуть бот в рабочее состояние.
- Реальный create → reschedule → cancel в YCLIENTS — отдельный разрешённый тест. До него заявлять готовность диалога и черновика, но не полную live-приёмку операций записи.

### 4. Завершение и ограничение дальнейшей работы

Пакет закрывается, когда реальные обычные запросы не дают технического fallback, ответы соответствуют ручной KB, первый/повторный вход корректны, draft переживает консультацию и исправление фактов, нет самовольных операций, админка подтверждает обработку. По каждому пункту — evidence или честное «не проверено».

Если после этого остаётся дефект, определить слой по evidence. Исправлять один общий источник ошибки; не добавлять отдельные regex-ветки под каждую фразу. Возвращаться к смене архитектуры только при воспроизводимой неспособности текущего разделения обеспечить согласованный сценарий, а не при очередном исключении API. Возможная безопасная консультация при отказе Router — отдельное улучшение устойчивости, не условие первого восстановления.

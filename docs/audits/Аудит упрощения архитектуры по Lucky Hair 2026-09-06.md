# Аудит упрощения архитектуры по Lucky Hair

Дата: 2026-09-06. Область: исходное задание из `pasted-text.txt`, найденного по скриншоту владельца; сравнение, решения и спецификация. Это не приёмка runtime и не разрешение на реализацию.

## Вывод

Первый пакет — консультации основного LLM по ручному системному промпту, без автоматической подстановки каталога YCLIENTS. Не нужен откат всего свободного диалога, новый оркестратор или переписывание записи. Каталог разделяется по использованию: консультационное grounding убирается, технические идентификаторы/связи услуги и специалистов остаются для записи.

Референс действительно проще, но не потому, что там всё говорит LLM: запись, перенос и значительная часть ответов детерминированы, есть кнопки и последовательные шаги. Копировать локальную запись Lucky Hair вместо YCLIENTS нельзя без потери операционных гарантий.

## 3. End-to-end сценарии

Общий путь нашего обычного текста: durable worker → local guards/PII → Security и Router → допуск Security → dispatch/ответ → validation → durable outbound. Callback и контакт имеют отдельный ограниченный детерминированный вход.

| Вход | Сейчас: фактическая развилка | Первый пакет |
|---|---|---|
| «Расскажи о крио» | consultation → catalog grounding → main LLM либо catalog shortcut → validator | consultation → main LLM с ручной KB → validator; никаких обращений к каталогу для ответа |
| «Сколько стоит?» с однозначной услугой в истории | Router восстанавливает услугу → `.ground()` → возможен `direct_reply` | LLM берёт цену из активной версии промпта, не из истории и не из YCLIENTS |
| «Хочу записаться» | booking → merge draft → следующий недостающий факт | Сохранить: уточнение услуги, затем реальные варианты; никакой записи от одного намерения |
| Услуга / мастер / слот | `_resolve_service` → `list_services`; `_offer_slots` → live port; callback выбора | Сохранить техническое сопоставление и проверку. Название в KB не равно provider ID |
| «А как подготовиться?» внутри draft | consultation → coordinator не выполняет booking action → ответ; draft остаётся | Ответ по KB, draft сохраняется; не объявлять обязательным запрет пошагового диалога |
| «Сколько стоит и запиши завтра» | Один route booking + topics; dispatch формирует локальное продолжение, консультационная часть дописывается `_combine_reply` | Цена из ручной KB + сохранённый booking next step. Не превращать topics в несколько исполняемых маршрутов |
| Перенос / отмена | booking_management → собственные записи → выбор → подтверждение → BookingService | Сохранить ownership, актуальность callback и state, повторную проверку слота и идемпотентность |
| Ошибка / низкая уверенность Router | pipeline clarification без действия | Сохранить fail-safe. Не копировать fallback consultation с искусственной confidence 1.0 |
| Сбой YCLIENTS / старый техкаталог | Поиск услуги/слотов или мутация не может подтверждаться; консультация сейчас также зависит от catalog status | Запись безопасно останавливается/уточняется, FAQ продолжает работать по ручной KB |
| Ошибка answer LLM при смешанном запросе | Ветка `LLMUnavailable/LLMNonRetryable` возвращает fallback без `local_reply`, хотя booking markup уже существует | Не терять локальный next step; если он отсутствует — безопасный fallback. Включить в контракт первого пакета |

Это трассировка, а не утверждение, что все ветки исправны. Конкретные дефекты продолжения/переноса и выбора специалиста вынесены в побочный аудит; их нельзя маскировать архитектурной переработкой или считать исправленными документами.

## 4. Какие поля Router действительно используются

| Данные V3 | Потребитель | Вывод |
|---|---|---|
| route/confidence | pipeline, coordinator | Оставить один первичный маршрут и gate уверенности |
| action/choice | Telegram coordinator: create/view/reschedule/cancel/continue и контекстный выбор | Удаление перенесёт классификацию в другой слой; пока оставить |
| services + legacy service | `conversation.merge_draft`, `_resolve_service`; также worker grounding | После удаления grounding остаётся booking-потребитель; legacy alias проверить отдельно, а не сломать совместимость |
| date/time_from/time_to/staff | [conversation.py](../../project/src/moroz/booking/conversation.py), merge/invalidation; `_offer_slots` | Нужны сбору данных в разном порядке и фильтрации живых слотов |
| topics | pipeline: нужно ли дополнить локальную реплику консультацией; worker: вид catalog reply | После удаления catalog останется mixed-response потребитель. Упрощать только вместе с его контрактом |

Упрощение до route/confidence не бесплатно: повторное извлечение услуги/времени в backend или второй LLM вызов могут увеличить суммарную сложность. Измерять количество веток и источников состояния на полном пути, а не длину JSON.

## 5. Ручная база: содержание и применение

> Историческое описание ниже относится к исходному состоянию. По последующему решению владельца редактор и hot reload удалены в ветке codex/reference-simplification; актуальное локальное evidence — в [приёмке пакета A](<Приёмка ручных консультаций 2026-09-06.md>). Старую цепочку save/reload не восстанавливать по этому разделу.

В [system.md](../../project/llm/prompts/system.md) v1.7 есть контакты, правила записи, общие объяснения крио/водородотерапии/коллагенария/криомассажа, подготовка и ограничения обещаний. Но это **не полный ручной прайс**. §7 и §10 прямо требуют каталог для названий/цен/длительностей/специалистов; §11.1 и часть примеров также на него ссылаются. В §9.3 осталась ссылка на «Мои записи» после удаления меню.

Для полноценной ручной KB недостаёт подтверждённой матрицы «публичная услуга/вариант → описание → цена с единицей → длительность процедуры и/или визита → подготовка → ограничения/эскалация», а также актуальных правил пакетов и депозитов. Медицинские обещания не расширяются.

[services_prices.md](../../project/data/services_prices.md) — историческая сводка 2026-07-07: крио, водородотерапия, прессотерапия, загар, массаж, лицо, программы/депозиты/сертификаты. Есть пометки «требуется подтверждение» и старое решение о приоритете YCLIENTS. Это кандидат для ручной сверки, **не разрешение скопировать июльские суммы как сегодняшние**. Файл не подключать в runtime и не синхронизировать с промптом автоматически.

### Существующая цепочка редактирования

`owner /prompt/save → версия PostgreSQL + атомарная запись общего system.md → Redis prompt:reload (version/request/hash) → worker _load_prompt → новый SecurityPipeline + extract_structured_facts → ack`.

- Owner/CSRF проверки уже есть; rollback создаёт новую версию. Не нужен второй редактор или таблица прайса.
- `_load_prompt` проверяет непустой текст/ожидаемый hash и строит новый prompt+facts до замены. Текущий запрос удерживает свой pipeline: не следует обещать переключение уже выполняющейся генерации.
- Подтверждённое отклонение откатывает запись; отсутствие ack означает «сохранено, применение не подтверждено», а не успешный reload. Pub/sub сам по себе не хранит пропущенные события; listener после reconnect не перечитывает файл автоматически. Это риск проверки восстановления, не повод проектировать новую шину.
- Compose монтирует общий `./llm/prompts` в admin и worker; staging override эти mounts не отменяет. Проверена конфигурация, не фактическая серверная синхронизация. Deployment должен сохранить owner-edited файл; image SHA один не доказывает содержимое смонтированного промпта.
- [validator.py](../../project/src/moroz/security/validator.py):388 извлекает facts из нового промпта. После удаления catalog merge новые явно записанные суммы попадают в allowlist при reload, удалённые — исчезают, если не встречаются ещё где-то в промпте.
- Это allowlist чисел, не проверка соответствия «услуга ↔ цена». Цена другой услуги может пройти. Формат `2200 ₽ — 6000 ₽` надёжнее для существующего extractor, чем `от 2200 до 6000 ₽` (первая граница без единицы). Семантическую точность нужно проверять сценариями, не приписывать regex несуществующую гарантию.

## 6. Каталог: что можно убрать, а что нельзя

| Потребитель | Назначение | Решение |
|---|---|---|
| Worker `resolve_catalog` → `generate_response(catalog=...)` | Подмешивание консультационных данных | Удалить из answer path |
| Pipeline `direct_reply`, `data_block`, catalog facts merge | Второй генератор консультации/прайса | Удалить консультационное использование |
| `admin/eval_runner.py` optional `catalog` | Альтернативный eval-контракт pipeline; обычный вызов по умолчанию None | Привести к тому же prompt-only контракту; не утверждать, что админка сейчас всегда грузит live catalog |
| `telegram.py:306` и `:824`, `CatalogRepository.list_services` | Разрешение услуги, provider ID, варианты специалистов при booking | Сохранить |
| `_build_yclients_services`, reader/repository/scheduler | Технический snapshot каталога | Сохранить до отдельного решения о свежести |
| `YCLIENTS_CATALOG_GROUNDING_ENABLED` | В worker отключает именно consultation repository reference | Флаг не равен отключению всего YCLIENTS. Одного выключения недостаточно: старый промпт требует каталог; нужна согласованная правка |

`CatalogSyncCoordinator.run` планирует следующую задачу через **1 час**; `list_services` отбрасывает snapshot старше **24 часов**. Остановить sync — значит со временем потерять технический поиск услуги. Слоты запрашиваются отдельно live; часовой snapshot не является кешем свободных окон.

Рекомендация: первый пакет сохраняет часовую периодичность как существующий технический запас свежести. Это не требование обновлять консультационные цены каждый час. Затем отдельно выбрать частоту/обновление по запросу с учётом 24h TTL, изменений услуг/мастеров и допустимого времени восстановления. Суточный cron без изменения TTL и запаса на сбой небезопасен. Таблицу и price-поля snapshot сейчас не удалять: это потребует отдельной миграции и проверки provider DTO.

## 7. История: что уже упрощено

Git подтверждает цепочку `834f77e` (backend FSM) → `776f525` (Telegram booking) → `1ceb43a` (consent/приветствие и этап меню) → `06e5c13` (контекстные цены/каталог) → `1bf7505`, `8178318`, `558b380` (UX/редактирование/меню 2×3) → `a51d37e` (план свободного диалога) → `e34437a` (V3) → текущий runtime.

В diff `a51d37e..82205a5` worker удалены `persistent_menu_command`, отдельное распознавание menu index и дублирующий text router. Большая Telegram category/service/staff/date wizard заменена merge draft; появился `conversation.py`. По четырём файлам router/worker/telegram/conversation diff даёт +1078/−1012 строк: это не доказательство уменьшения общего кода, но доказательство замены механизма. Постоянное меню и витрину нельзя предлагать «удалить впервые» второй раз.

Полный rollback вернул бы удалённые menu paths и потерял бы полезное заполнение фактов в разном порядке. Владелец rollback не выбирал. Реальная оставшаяся избыточность первого пакета — параллельные источники консультации (ручной текст + catalog block + direct reply) и противоречивые правила, не сама state machine транзакций.

## 8. Очерёдность и решения владельца

1. [Первый пакет: ручная консультационная KB](../superpowers/specs/2026-09-06-manual-consultation-knowledge-design.md). Убирает конкретную зависимость, не меняет модель записи.
2. После него — отдельно оценить Router legacy aliases/topics и оставшиеся ветки формирования ответа на реальных сценариях. Не вводить новый orchestration framework.
3. Затем — UX входа/возврата в запись и частота технического sync. Рекомендация входа: свободное «хочу записаться»; контекстная кнопка допустима, постоянный каталог не нужен. В первом пакете текущий вход сохраняется.

До внедрения/приёмки нужны: подтверждённое содержимое ручного прайса; согласие с narrow spec; отдельно решение о входной кнопке, если менять текущий UX. Рекомендуемая политика расхождений: в консультации не подменять цену YCLIENTS, а при выявленном операционном конфликте не обещать неподтверждённые условия, уточнять у администратора. Эти вопросы не блокируют завершение самого аудита.

## P1-1. Тесты очищают Redis локальных сервисов

Места: `project/docker-compose.yml:15`, `project/tests/e2e/test_privacy_gate.py:229`, `project/tests/e2e/test_message_delivery.py:132`, аналогичные integration fixtures.

Compose передаёт сервису `test` тот же `REDIS_URL`, что рабочим локальным сервисам. Fixtures подключаются к этому URL и вызывают `flushdb()` при подготовке и завершении. Отдельная тестовая Redis-база/инстанс и проверка назначения перед очисткой отсутствуют. Обычный запуск E2E через документированный Compose-контур поэтому может удалить локальный контекст, transient consent state и другие ключи выбранной базы.

**Evidence:** во время расширенного audit-прогона такие fixtures уже выполнились. Прогон остановлен; выбранная локальная Redis-база была очищена. Предварительного снимка ключей не было, поэтому объём потери кеша неизвестен; восстановление прежнего Redis-состояния не выполнялось. Тестовые PostgreSQL-операции направлялись в disposable БД, staging/production не использовались. Пользователь уведомлён сразу после обнаружения.

**Исправление:** отдельный disposable Redis для тестов и защита fixtures от подключения к обычному runtime URL. Для продолжения самого аудита поднят временный Redis без volume, переданный тестам через override `REDIS_URL`.

## P1-2. Миграция 0026 не работает после Windows checkout

Места: `project/migrations/versions/0026_router_v3.py:24`, `.gitattributes:1`, `project/migrate/Dockerfile:15`.

Миграция вычисляет SHA256 сырых байтов `router_dataset_v3.json` при импорте. Для V1/V2 в `.gitattributes` есть обязательный LF, для V3 правила нет. Текущий чистый Git checkout имеет `i/lf w/crlf`. Семантически JSON не изменился, но его SHA256 отличается, и Alembic завершается до выполнения сценария. Docker COPY сохраняет эти байты, поэтому сборка migration-образа из данного checkout также переносит проблему в образ.

**Evidence:**

- первый свежий Docker gate: `325 passed, 15 errors in 42.91s`;
- все 15 ошибок — setup E2E, `RuntimeError: Router v3 dataset integrity mismatch for migration 0026`;
- SHA256 текущего файла: `2c2e17dc03cd798fd04168e3405932485510499a2b1c94383d8de58e1b68947b`;
- после замены CRLF → LF только в памяти: `a0d23048e2ce0d396985bb82ff0832d7b63f0a0f7296227554cb0f6984d736a1`, точно равен константе миграции;
- Git-экспорт с `core.autocrlf=false` имеет ожидаемый LF-хеш; обычный экспорт при текущей настройке также получил CRLF.

**Исправление:** закрепить LF для V3 и проверить защиту checksum на обеих формах переноса строк, ориентируясь на уже существующие миграции security/validator/compact. Отключать сам контроль целостности не требуется.

## P1-3. Продолжение переноса превращается в создание новой записи

Места: `project/src/moroz/messaging/router.py:123` — инструкция «Для cancel_draft и continue выбирай booking»; `project/src/moroz/booking/telegram.py:164`, `:184`.

**Сценарий:** клиент начинает перенос существующей записи, получает вопрос о новой дате и отвечает «6 сентября». Router вправе вернуть предусмотренное собственным prompt решение `route=booking, action=continue, date=2026-09-06`.

`handle()` передаёт управление `_handle_management()` только для `route=booking_management`. Для `booking/continue` активный сценарий `reschedule` попадает в условие `scenario.kind != "create"`: он закрывается как `booking_flow_switched`, затем создаётся новый create draft. Новая дата сохраняется уже в другой операции, а услуга/ссылка на исходную запись теряются. Если клиент завершит этот новый сценарий и нажмёт подтверждение, будет создана дополнительная запись, исходная останется на старом времени. Mutation без кнопки не происходит.

**Исправление:** `continue` должен продолжать текущую операцию с учётом её kind; переход к новой create-операции требует явного намерения создать новую запись. Согласовать это правило в router prompt и backend dispatch. Покрыть перенос с датой отдельным сообщением, а не только одним полным запросом и callback-выбором.

## P1-4. Изменение параметров переноса повреждает его состояние

Места: `project/src/moroz/booking/conversation.py:14`, `:60`; `project/src/moroz/booking/telegram.py:532`, `:801`, `:846`, `:914`; `project/src/moroz/booking/service.py:217`.

Это отдельная проблема даже при правильном `route=booking_management`.

**Сценарий A:** начать перенос без даты, затем передать дату отдельным semantic turn. `merge_draft()` вызывает `_clear_slot()`, который удаляет `starts_at`. В create это время выбранного слота, но в reschedule это время **исходной существующей записи**, нужное для проверки её неизменности. `_choose_slot()` для переноса заполняет только `new_starts_at`. После кнопки подтверждения `BookingService._handle_change()` читает отсутствующий `scenario.state["starts_at"]` и получает `KeyError`, вместо выполнения переноса или штатной эскалации. Изменение времени/специалиста даёт тот же эффект.

**Сценарий B:** выбрать слот переноса, получить подтверждение и исправить дату. `_handle_management()` и `_checkpoint()` сохраняют фазу `awaiting_confirmation`, затем `_offer_slots()` выдаёт новые кнопки со step=`slot`. Но `_handle_callback()` принимает такой выбор только в фазе `collecting`. Все новые кнопки отклоняются как устаревшие, хотя пользователь только что их получил.

**Исправление:** разделить исходные данные существующей записи и сбрасываемые параметры нового слота; при изменении подтверждаемого переноса возвращать collecting-фазу. Отдельно проверить обе ветки — устранение только checksum или только ошибки маршрута их не исправляет.

## P2-1. Неразрешённый специалист перестаёт блокировать следующий шаг

Места: `project/src/moroz/booking/conversation.py:86`; `project/src/moroz/booking/telegram.py:193`, `:340`, `:403`, `:515`.

**Сценарий:** клиент называет существующую услугу и неизвестного/неоднозначного специалиста. Бот спрашивает имя специалиста. Следующим сообщением клиент сообщает только дату.

При первом сообщении `_select_service()` сохраняет service ID и `staff_query`, но выходит без разрешённого `staff_id`/`staff_name`. На следующем сообщении проверка предпочтения выполняется лишь при `decision.staff is not None`. В `next_requirement()` требования `staff` нет, поэтому бот переходит к слотам без staff-фильтра. В состоянии может отсутствовать `staff_name`, который затем напрямую читается при формировании подтверждения и вызывает `KeyError`.

**Исправление:** сохранять и проверять незавершённое разрешение предпочтения как условие готовности черновика на каждом продолжении. Произвольная дата не должна молча означать согласие на любого специалиста.

## P2-2. Сбой основной LLM скрывает уже подготовленный результат записи

Места: `project/src/moroz/security/pipeline.py:241`, `:342`; `project/worker/main.py` — сохранение `booking_reply.delivery_options` в outbound.

**Сценарий:** смешанное сообщение содержит запись и информационную тему, например просьбу перенести запись и вопрос о подготовке. Dispatch уже подготовил локальный результат и кнопки, затем основная LLM недоступна.

Для `route.topics` pipeline сохраняет результат dispatch в `local_reply` и обращается к answer gateway. В обработчике `LLMUnavailable/NonRetryableLLMError` возвращается только `SAFE_OUTPUT_FALLBACK`, без `_combine_reply(..., local_reply)`. Worker при этом оставляет кнопки из `booking_reply`. Пользователь получает общий fallback с кнопками, но без вопроса, объяснения следующего шага или резюме действия. При шаге подтверждения может отсутствовать описание подтверждаемой операции.

**Исправление:** сохранять локальную часть и в ветке недоступности answer provider, как это уже сделано при исчерпании попыток validator. Проверить смешанный запрос вместе с provider outage и итоговым outbound markup.

## P2-3. Четвёртая будущая запись недоступна для управления

Места: `project/src/moroz/booking/telegram.py:564`, `:580`, `:590`; `project/src/moroz/booking/repository.py:167`.

**Сценарий:** у клиента четыре или более будущих записей, созданных в этом чате; нужно отменить или перенести четвёртую.

Repository возвращает все собственные будущие записи, но coordinator сохраняет только `owned[:3]`. Механизма уточнения/поиска среди остальных нет. Следующие semantic turns в management-state используют прежний набор choices; названия услуг для фильтрации записей не применяются, а `decision.date` сохраняется как `requested_date` переноса. Снятие черновика и повторный вход снова показывают те же первые три.

**Исправление:** ограничивать размер показанного набора после уточнения целевой записи, сохраняя возможность выбрать остальные свои записи текстом. Возвращать полный кнопочный список не требуется.

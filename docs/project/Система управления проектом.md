# Система управления проектом Moroz i Solntse Bot

## Зачем нужен этот документ

Этот файл описывает постоянные правила координации проекта. Он не содержит текущий релизный статус и не конкурирует с дорожной картой.

Главная причина прежней путаницы: документы разных типов одновременно отвечали на вопрос «где мы сейчас». Стартовая ступень оставалась в `AGENTS.md`, подробная история росла внутри roadmap, master plan показывал незавершённые фазы, а локально готовый код иногда находился дальше развёрнутого staging. Каждый факт мог быть правильным в своём контексте, но общего пульта не было.

## Как проходит работа

Универсальная формула проекта:

**Идея / референс → gap-анализ → решение владельца → ТЗ или ADR/spec → Roadmap → release plan → implementation plan → код и тесты → review → Git/changelog → rollout evidence → Roadmap.**

Коротко:

1. Референс показывает возможность, но ещё ничего не требует.
2. Gap-анализ сравнивает референс с нашей целью и уже существующим кодом.
3. Владелец принимает, откладывает или исключает решение.
4. Принятое изменение получает нужный уровень описания: ТЗ для цели, ADR/spec для решения, plan для исполнения.
5. Только выбранная текущая работа попадает в `Now`.
6. Локальная готовность доказывается тестами и review, но не называется deployment.
7. Deployment доказывается commit/tag, image IDs, schema, smoke, logs и rollback.
8. После evidence обновляется единственный текущий status source — roadmap.

## Правила обновления

### Новая идея

Записать источник, проблему и ожидаемую пользу. Если меняется продуктовая цель — обновить ТЗ или создать ADR/spec. После решения владельца поставить инициативу в `Now / Next / Later`. Подробную spec создавать только для выбранного `Now` или для обязательного release blocker.

### Начало задачи

Зафиксировать exact base branch/commit, создать изолированную ветку или worktree, связать roadmap с одной active spec/plan и явно ограничить изменяемые файлы, внешние системы и среды.

### Во время реализации

Одна ветка решает одну связанную проблему. Независимые блоки можно параллелить, если они не меняют общую state boundary. Merge, миграции и rollout идут последовательно после общего review и полного gate.

### Завершение задачи

Получить тестовые и review evidence, сделать логический commit, добавить значимую запись в changelog и обновить roadmap. Не объявлять deployed до runtime evidence. Implementation plan после завершения остаётся историей исполнения, а не новым backlog.

### Релиз

Зафиксировать candidate commit/tag, пройти полный gate и review, сохранить rollback, выполнить rollout и runtime-проверку. Только после этого обновить roadmap как `развёрнуто`. Если внешний API заблокирован, отдельно записать доказанный локальный результат, точный внешний blocker и действие владельца.

## Референсы

Правильный путь для внешнего решения:

**External reference → датированный audit → решение владельца → roadmap → spec → plan → implementation.**

Референс не становится требованием автоматически. Мы переносим не код, а доказанную полезную идею с учётом своей архитектуры, privacy boundary и операционных ограничений.

Для Router, Input Security, Validator, Compact Context и их evaluations действует дополнительный обязательный gate: `docs/project/Контракт адаптации LLM-референса Володи.md`. До design исполнитель изучает зафиксированный commit `5398f90` и документирует решения «взять / адаптировать / отклонить».

## Основа в индустриальных практиках

- Product roadmap отвечает за направление и приоритеты, но не заменяет журнал или детальную реализацию.
- Один упорядоченный backlog служит единственным источником предстоящей работы команды.
- ADR/spec фиксирует контекст, решение и последствия, чтобы решение не приходилось восстанавливать по коммитам.
- Release status опирается на неизменяемый commit/artifact и runtime evidence, а не на имя ветки или фразу «код готов».

Полезные первичные и отраслевые ориентиры: [Scrum Guide](https://scrumguides.org/scrum-guide.html), [AWS Prescriptive Guidance по ADR](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html), [Atlassian о product roadmap](https://www.atlassian.com/agile/product-management/product-roadmaps).

## Защита от повторения путаницы

- не хранить текущую стадию в `AGENTS.md`;
- не записывать будущие задачи в `changelog.md`;
- не считать локальный commit развёрнутым;
- не создавать подробную spec для обычного `Later`;
- не копировать весь backlog из референса;
- не вести второй status source в Notion, Jira или другом файле без явного отказа от корневой roadmap;
- не смешивать target architecture и фактический runtime status;
- при противоречии исправлять документ-владелец вопроса и оставлять в остальных только ссылку.

## Быстрая проверка перед любым следующим проектом

Перед стартом спросить пять вещей:

1. Где единственный текущий статус?
2. Где зафиксирована целевая версия продукта?
3. Какое решение владельца переводит идею в backlog?
4. Чем локальная готовность отделена от deployment?
5. Какие exact evidence закроют задачу?

Если на каждый вопрос есть один конкретный ответ и один документ-владелец, координация выстроена правильно.

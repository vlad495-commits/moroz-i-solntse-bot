- Реализовано ядро Telegram Production V1: webhook, consent/privacy gate, durable inbox/outbox, worker, scheduler, админка и read-only YCLIENTS projection.
- Закрыты release blockers удаления данных: YCLIENTS suppression, deletion ↔ projection race и privacy fence перед Telegram outbound.
- Release candidate объединён, прошёл полный Docker gate, развёрнут на staging и проверен сценарием rollback → restore.
- Проектные документы разделены по ролям; подробная история сохранена в архиве и changelog.

## Активная работа

- Release-направление: завершить независимую ручную приёмку Telegram и админки; подключение YCLIENTS отложено по решению владельца до отдельного возврата к этапу.
- Управление контентом: системный промпт, база знаний и статические бизнес-правила меняются только локально, версионируются Git и попадают на сервер через commit-pinned Docker-деплой. Админка не является источником изменений этого контента; отдельное DB-версионирование знаний не создаётся.
- Доступ к staging-админке: владелец подтвердил успешный вход индивидуального технического аккаунта `Влад` с паролем и TOTP. Отдельный аккаунт заказчицы откладывается до безопасной связи с ней.
- Решение по владению: текущее бесплатное непубличное приложение остаётся dev/test; production-приложение создаётся и контролируется заказчиком в его действующем YCLIENTS.
- Спецификация подключения: `docs/superpowers/specs/2026-08-20-customer-owned-yclients-app-design.md`.
- План реализации подключения приложения заказчика: `docs/superpowers/plans/2026-08-20-customer-owned-yclients-app-onboarding.md`.
- Правило возобновления этапа: только после отдельного решения владельца и безопасного доступа заказчицы к кабинету YCLIENTS выполнять подключение последовательно по указанному плану; логин, пароль, токены и TOTP не записывать в чат, Git или проектные документы.

## Доказано

- Полный Docker release gate: `1259 passed in 594.78s`.
- Независимый review нашёл deletion ↔ projection race; после TDD-fix повторный review не оставил Critical/Important blockers.
- Staging smoke: четыре app runtime healthy и совпадают с candidate image IDs; scheduler synthetic job завершился штатным `skipped`; HTTPS, webhook и safe log scan прошли, log counters — `0/0/0/0`.
- Backward compatibility: предыдущие bot/worker healthy на additive schema `0012`; откат образов и восстановление candidate подтверждены без DB downgrade.
- YCLIENTS диагностика: user permissions endpoint — `200`; records-list endpoint — `403` во всех безопасных read-only вариантах. В live-настройках dev/test-приложения обнаружено, что право «Просматривать список записей» не выбрано; это более конкретная вероятная причина `403`, чем завершившийся тестовый тариф.
- Project governance: обычный Docker test-profile видит только allowlisted документы; governance contract `4 passed`, совместный governance/architecture gate — `12 passed`, Compose config — exit `0`.

## Блокеры

- YCLIENTS production acceptance отложена: приложение заказчика ещё не создано и не подключено, а текущий dev/test-контур не имеет выбранного права «Просматривать список записей» и возвращает `403` на records-list.
- Production launch не выполняется до возобновления и завершения YCLIENTS acceptance, создания индивидуального аккаунта заказчицы с TOTP и подтверждённого входа через безопасный канал.

## Что нужно от владельца

- До возобновления YCLIENTS-этапа и связи с заказчицей новых действий по внешним доступам не требуется.
- При возобновлении согласовать безопасную совместную сессию создания production-приложения YCLIENTS и индивидуального TOTP-аккаунта заказчицы; логин, пароль, токены и TOTP не передавать в Git или чат.
- Отдельно разрешить одну синтетическую create → get → reschedule → get → cancel проверку только после успешного read-only gate; реальные записи клиентов не изменять.
